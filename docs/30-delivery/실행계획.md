# 1단계 기술 흐름 프로토타입 실행계획

- 소유자: `delivery-lead`
- 상태: 사용자 승인 완료
- 승인 일시: 2026-08-22 21:10 KST
- 기간: 기본 5주, 필요 시 1주 보완(전체 4~6주)
- 기준: `../10-scope/1단계-기술-프로토타입-목표-범위-인수조건.md`
- 원본 대조: `../00-input/원본-요구사항-RFP.md`

## 1. 목적

광주·전남 복지용구 위탁소독 업무의 핵심 흐름을 로컬 환경에서 검증하기 위해 1단계 기술 프로토타입의 작업 순서, 담당 BOT, 선행 조건, 산출물과 완료 기준을 정의한다.

1단계의 목표는 실사용 시스템 출시가 아니라 다음 기술 흐름을 실제로 실행하고 데이터 보존과 출력 정합성을 검증하는 것이다.

```text
접수 → 수거완료 → 소독완료 → 배송완료
```

가상 데이터 1건 이상이 접수부터 배송완료까지 처리되고, 상태 이력·재시작 후 데이터 보존·필터·통계·PDF·엑셀이 실제로 작동하면 1단계 목표를 달성한 것으로 본다.

## 2. 기준과 우선순위

### 2.1 기준 문서

1. 단일 범위 기준: `../10-scope/1단계-기술-프로토타입-목표-범위-인수조건.md`
2. 원본 요구사항: `../00-input/원본-요구사항-RFP.md`
3. 공통 작업 규칙: `../../.hermes.md`

문서 간 충돌이 발생하면 승인된 1단계 범위 문서를 우선한다. 범위 또는 인수 조건 변경은 구현 전에 영향 분석과 사용자 승인을 거쳐 기준 문서에 반영한다.

### 2.2 실행 우선순위

1. 업무 목표·범위·인수 조건 확정
2. 전체 업무 흐름 완성
3. 사용성
4. 데이터 정확성
5. 자동화

보안과 데이터 손실 방지는 위 우선순위와 관계없는 기본 조건으로 적용한다.

## 3. 1단계 범위

### 3.1 포함 범위

- 고정 사업소 1~3개를 사용하는 접수폼
- 수거 희망일, 장소 유형, 주소 입력
- 전동침대, 휠체어, 기타 소형 용구 수량 입력
- 필수값, 날짜, 수량에 대한 서버 측 검증
- 접수번호, 최초 상태, 생성 시각 자동 기록
- 정의된 순서로만 가능한 상태 전이
- 모든 상태 변경 시각과 완료일 보존
- `접수` 상태에서만 접수 정보 수정
- 접수 생성과 상태 전환 시 화면 알림
- 접수 목록·상세 조회
- 수거 희망일 기간·사업소·상태 필터
- 기간·사업소·상태·품목 수량 통계
- 현재 필터 결과 기준 엑셀 다운로드
- `소독완료` 상태부터 빈 PDF 다운로드
- 애플리케이션 재시작 후 데이터 보존
- PC Chrome 및 모바일 너비 반응형 화면

### 3.2 제외 범위

- 실제 카카오 알림톡 발송
- 비즈뿌리오·쏠라피 API 연동
- 알림톡 템플릿 신청·검수·승인
- 실제 공단 소독증명서 생성
- PDF 내 사업소·시리얼·소독일·직인 삽입
- 로그인·인증·권한
- 외부 또는 클라우드 배포
- 사업소 관리 화면
- 기사 계정·기사 배정·권역 관리
- 품목별 시리얼 관리
- 접수 삭제
- 상태 건너뛰기 또는 역방향 변경
- 실제 고객 데이터 사용
- A/S 점검 요청과 기타 비고
- 운영 및 하자 보수

원본 RFP의 A/S 요청, 기사 배정, 실제 알림톡, 실제 증명서, 공단 실양식은 승인된 1단계 범위에서 제외되므로 이번 계획에 포함하지 않는다.

## 4. 추진 체계

| 역할 | 책임 |
|---|---|
| 사용자(Product Owner) | 범위·주요 기술·비용·중대한 변경·최종 결과 승인 |
| `delivery-lead` | 실행계획, 시스템 설계, 작업 선점, 결과 통합, 위험·결정 관리 |
| `ux-designer` | 세 화면 UX, 입력·오류 상태, 모바일 규칙, 디자인 토큰, 접근성 기준 |
| `local-builder` | 데이터 모델, 애플리케이션, DB, PDF·엑셀, 자동화 테스트 구현 |
| `quality-gate` | 요구사항 추적, 독립 실행 검증, 데이터 정합성·보안·접근성 검사, 출시 판정 |

### 4.1 작업 통제 원칙

- 모든 쓰기 작업은 `delivery-lead`가 작업번호와 수정 허용 경로를 배정한 후 시작한다.
- `docs/30-delivery/진행현황.md`의 활성 선점표에 등록되지 않은 파일은 수정하지 않는다.
- 하나의 파일은 동시에 한 BOT만 수정한다.
- 담당 경로 밖의 변경이 필요하면 수정을 중지하고 선점 범위 확장을 요청한다.
- 다른 BOT 소유 파일은 직접 수정하지 않고 변경 요청을 전달한다.
- 담당 BOT은 변경 파일, 실행한 검증, 실제 결과, 남은 위험을 보고한다.
- `delivery-lead`가 인계를 확인하고 선점을 해제한 결과만 `quality-gate`가 최종 검증한다.
- 독립 검증 전에는 1단계 완료를 선언하지 않는다.
- WP-05 이후 각 구현 작업은 착수 전에 `delivery-lead`가 작업번호, 대상 WP, 담당 BOT, 선행 조건, 수정 허용 경로, 구현 동작, 참조 설계, 작성할 테스트, 검증 방법, 완료 기준, 제외 범위와 완료 보고 형식을 포함한 실행 지시서를 발행한다.
- 주요 실행 지시서는 `docs/30-delivery/prompts/**`에 보존하며, 실행 지시서는 승인된 범위·설계·인수 조건을 변경하지 않는다.

## 5. 일정

기본 일정은 5주이며 차단 결함이나 로컬 실행환경 문제가 발생하면 1주를 보완 기간으로 사용한다. 범위가 안정적이고 결함이 적으면 4주 완료를 허용하되 인수 조건을 축소하지 않는다.

| 기간 | 마일스톤 | 주요 결과 |
|---|---|---|
| 1주차 | 설계 기준 확정 | 시스템 설계, UX 명세, 디자인 토큰, 데이터 모델, 인수조건 추적표 |
| 2주차 | 접수·저장 기반 완성 | 로컬 실행환경, 영속 저장소, 접수 생성·검증·수정, 재시작 보존 |
| 3주차 | 상태 흐름 완성 | 목록·상세, 순차 상태 전이, 상태 이력, 완료일, 화면 알림 |
| 4주차 | 출력·통계 완성 | 필터, 통계 대시보드, 엑셀, 빈 PDF 다운로드 |
| 5주차 | 통합·독립 검수 | 전체 시나리오, PC·모바일 검증, 결함 수정·재검증 |
| 6주차 | 조건부 보완 | 차단 결함 수정, 회귀 검증, 문서 정리, 최종 승인안 |

실제 알림톡, 실제 증명서, 인증 또는 외부 배포가 추가되면 이 일정과 별도로 영향 분석 후 재산정한다.

## 6. 단계별 실행계획

### WP-01 시스템 설계 작성

- 담당: `delivery-lead`
- 선행 조건: 실행계획 사용자 승인
- 수정 경로: `docs/20-design/시스템-설계.md`
- 산출물:
  - 기술 스택과 선택 이유
  - 로컬 실행 구조와 주요 모듈
  - 데이터 저장 및 재시작 보존 방식
  - 상태 전이 검증 책임 위치
  - 입력에서 DB, 화면, 통계, 엑셀로 이어지는 데이터 흐름
  - 테스트 및 실행 방식
- 완료 기준:
  - 1단계 범위만 다룬다.
  - 미래용 추상화나 미사용 확장 지점을 만들지 않는다.
  - `local-builder`가 구현 가능한 수준으로 책임 위치가 명확하다.
  - 주요 기술 선택에 사용자 승인을 받는다.

### WP-02 UX 및 디자인 명세

- 담당: `ux-designer`
- 선행 조건: 실행계획 사용자 승인
- 수정 경로:
  - `docs/20-design/UX-화면-명세.md`
  - `docs/20-design/디자인-토큰.md`
- 산출물:
  - 접수폼, 접수 목록·상세, 통계 대시보드 흐름
  - 필드별 정상·오류·비활성 상태
  - 모바일·PC 레이아웃
  - 명시적 레이블과 오류 메시지
  - 상태를 색상 외 텍스트로도 구분하는 규칙
  - 화면별 구현 인수 조건
- 완료 기준:
  - 승인된 필드와 필터가 빠짐없이 추적된다.
  - 모바일 너비에서 핵심 흐름이 가로 스크롤에 의존하지 않는다.
  - 구현자가 추가 해석 없이 화면 상태를 구현할 수 있다.

### WP-03 데이터 모델 설계

- 담당: `local-builder`
- 선행 조건: WP-01 설계 방향 확정
- 수정 경로: `docs/20-design/데이터-모델.md`
- 산출물:
  - 사업소, 접수, 품목별 수량, 현재 상태, 상태 변경 이력 모델
  - 완료일, 생성·수정 시각 규칙
  - 데이터 제약조건과 인덱스 근거
- 완료 기준:
  - 현재 상태와 모든 상태 변경 시각을 함께 보존할 수 있다.
  - 접수 삭제를 전제로 한 설계가 없다.
  - 통계와 엑셀이 동일한 원본 데이터를 사용할 수 있다.
  - 재시작 후 보존 가능한 저장 구조가 정의된다.

### WP-04 인수조건 추적표 작성

- 담당: `quality-gate`
- 선행 조건: 범위 문서 및 WP-01~03의 검토 가능한 초안
- 수정 경로: `docs/40-quality/인수조건-체크리스트.md`
- 산출물:
  - 범위 문서 8장의 각 조건과 연결된 검증 항목
  - 정상, 오류, 경계값, 중복 요청 시나리오
  - 상태 전이, 데이터 보존, 엑셀 정합성 검증 절차
- 완료 기준:
  - 모든 인수 조건이 최소 하나의 검증 항목과 연결된다.
  - 실제 실행 항목과 문서 검토 항목이 구분된다.

### 1주차 설계 게이트

다음 조건을 모두 충족해야 구현을 시작한다.

- 기술 스택 사용자 승인
- 시스템 설계 검토 완료
- UX 명세와 데이터 모델 간 필드 불일치 없음
- 인수조건 추적 누락 없음
- 구현 범위와 제외 범위 재확인

### WP-05 로컬 실행환경과 영속 저장소 구성

- 담당: `local-builder`
- 선행 조건: 1주차 설계 게이트 통과
- 수정 경로: `app/**`
- 산출물:
  - 승인된 기술 스택의 최소 프로젝트
  - 고정 사업소 초기 데이터
  - 로컬 영속 저장소
  - 실행·종료·재실행 절차
  - 최소 자동화 테스트 기반
- 완료 기준:
  - 문서화된 단일 명령 또는 절차로 실행된다.
  - 초기 사업소가 중복 생성되지 않는다.
  - 종료·재실행 후 저장 데이터가 유지된다.

### WP-06 접수 생성·검증·수정

- 담당: `local-builder`
- 선행 조건: WP-02, WP-03, WP-05 완료
- 수정 경로: `app/**`
- 구현 내용:
  - 접수폼과 서버 측 입력 검증
  - 접수번호 자동 부여
  - 최초 상태 `접수`와 생성 시각 기록
  - `접수` 상태에서만 수정
  - 접수 생성 화면 알림
- 오류 검증:
  - 필수값 누락
  - 모든 품목 수량 0
  - 음수 또는 정수가 아닌 수량
  - 오늘 이전 수거 희망일
- 완료 기준:
  - 정상 접수 1건이 저장된다.
  - 오류 입력이 저장 전에 거부된다.
  - 접수번호, 최초 상태, 생성 시각이 저장된다.
  - `접수` 외 상태에서는 수정이 거부된다.

### WP-07 상태 전이와 이력

- 담당: `local-builder`
- 선행 조건: WP-06 완료
- 수정 경로: `app/**`
- 허용 상태 전이:

```text
접수 → 수거완료 → 소독완료 → 배송완료
```

- 구현 내용:
  - 바로 다음 상태로만 전환
  - 모든 상태 변경 시각 기록
  - 상태 전환 화면 알림
  - 배송완료 시 완료일 기록
  - 중복 요청 시 상태 이력 중복 방지
- 완료 기준:
  - 정상 순차 전이가 성공한다.
  - 건너뛰기, 역방향, 배송완료 이후 변경이 거부된다.
  - 실패한 변경이 현재 상태나 이력을 부분 변경하지 않는다.
  - 상태 이력이 생성 순서대로 조회된다.

### WP-08 접수 목록·상세·필터

- 담당: `local-builder`
- 선행 조건: WP-06, WP-07 완료
- 수정 경로: `app/**`
- 구현 내용:
  - 접수 목록과 상세

## 10. 일정·견적 가정

- 개발자는 1명이며 BOT이 설계·구현·검증을 보조한다.
- 개발은 로컬 PC 한 대에서 수행한다.
- 1단계는 로컬 전용 기술 프로토타입이다.
- 외부 서비스 사용료와 운영 인프라 비용은 발생하지 않는 것을 전제로 한다.
- 카카오 알림톡, 클라우드, 도메인, SSL, 실제 공단 양식 작업은 제외한다.
- 기술 스택은 기존 설치 도구와 Java 표준 생태계를 우선한다.
- 신규 유료 도구나 서비스는 사용자 승인 전 도입하지 않는다.
- 실제 업무 범위가 추가되면 4~6주 일정을 유지한다고 보장하지 않으며 영향 분석 후 재산정한다.

## 11. 착수 승인 항목

구현 전 사용자가 다음 항목을 승인해야 한다.

1. 일정 기준: 기본 5주, 필요 시 1주 보완
2. 범위 기준: 승인된 1단계 범위를 유지하고 A/S, 기사, 실제 알림톡, 실증명서를 제외
3. 품질 기준: 자동화 테스트와 `quality-gate`의 브라우저·DB·엑셀 독립 대조를 모두 완료 조건에 포함
4. 착수 순서: 실행계획 승인 → 시스템·UX·데이터 설계 → 기술 스택 승인 → 구현

승인 전에는 시스템·UX·데이터 설계 작업을 배정하지 않는다.
