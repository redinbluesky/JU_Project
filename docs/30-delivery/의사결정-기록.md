## DEC-003 — 1단계 접수번호 표시 형식 승인

- 결정: 접수번호는 DB 시퀀스 기반 `R-{10자리 일련번호}` 형식을 사용한다. 예시는 `R-0000000001`이다. 런타임 트랜잭션 롤백 등으로 발생한 번호 공백을 허용하고 이미 소비한 번호는 재사용하지 않는다.
- 이유: 날짜별 `MAX+1` 방식의 동시성 충돌을 피하고, 단일 DB 시퀀스로 중복 없는 접수번호를 단순하게 부여하기 위해서다.
- 영향: 데이터 모델과 이후 구현·화면·PDF·엑셀의 접수번호 표현을 이 형식으로 통일한다. 번호는 순서 식별용이며 연속성을 업무 완료 조건으로 사용하지 않는다.
- 재검토 조건: 실제 운영에서 날짜 포함, 거래처별 번호 또는 법정 서식에 따른 번호 규칙이 요구되는 경우
- 사용자 승인: 2026-08-22 21:55 KST, Product Owner 명시 승인

## DEC-005 — 기술 스택을 Java/Spring에서 Python/FastAPI로 전환

- 결정: DEC-002에서 승인한 Java 21 + Spring Boot 스택을 폐기하고 Python 3.11+ + FastAPI + SQLAlchemy + Alembic + SQLite 파일 DB로 전환한다. PDF/엑셀 라이브러리는 구현 착수 시 별도 확정한다.
- 이유: Product Owner가 시니어 Java 풀스택 개발자이자 파이썬 가능자로서 파이썬 구현을 직접 요청했다. DEV-001 기술 기반 검증이 실패·중단된 상태였고(Flyway 미적용, Maven Wrapper 반복 실패, `app/**` 부분 파일 17개 미검증), 실질 구현 자산이 거의 없어 전환 비용이 낮은 시점이었다.
- 영향:
  - DEC-002는 이 결정으로 대체되어 더 이상 유효하지 않다.
  - 기존 `app/**`(Java, 검증되지 않은 부분 파일)를 삭제하고 새 Python 뼈대로 교체했다. `runtime/db`, `runtime/pdf`, `runtime/xlsx`의 Java 산출물(H2 DB 파일, 테스트 PDF/XLSX)도 함께 삭제했다.
  - `docs/00-input`, `docs/10-scope`, `docs/20-design/UX-화면-명세.md`, `docs/20-design/디자인-토큰.md`, `docs/20-design/데이터-모델.md`의 업무 요구사항·범위·UX·데이터 모델 내용은 언어 독립적이므로 재사용한다. 단 `데이터-모델.md`의 JPA/Flyway/H2 특정 구현 세부는 SQLAlchemy/Alembic/SQLite 기준으로 `local-builder`가 재작성해야 한다.
  - `docs/20-design/시스템-설계.md`의 3~21절(Java/Spring 특정 스택·구조·빌드 명령)은 무효화되었으며 Python 스택 기준으로 재작성이 필요하다. 1·2·8·13·14·15·16.2절의 업무 규칙(상태 모델, PDF/엑셀 정합성 규칙, 오류 처리, 검증 절차)은 언어 독립적이므로 유지한다.
  - `docs/40-quality/인수조건-체크리스트.md`의 48개 인수조건은 업무 요구사항 기준이라 재사용하되, Java 특정 검증 방법(JUnit/MockMvc 등)이 언급된 항목은 Python 대응 방법으로 갱신 필요.
  - 신규 프로젝트 뼈대: `app/main/{api,models,schemas,services,db}`, `migrations/`, `tests/`.
- 재검토 조건: FastAPI/SQLAlchemy 기반 최초 기술 기반 검증 실패, PDF/엑셀 라이브러리 선택 시 중대한 제약 발견, Product Owner의 재변경 요청
- 사용자 승인: 2026-08-23, Product Owner 명시 요청 및 진행 승인
