## 작업

### 1. 접수번호 채번을 카운터 테이블 방식으로 교체 (`app/main/services/request_service.py`)

데이터-모델.md 3.3절 채번 절차를 그대로 구현하라:
```python
# SQLite 3.35+ UPDATE ... RETURNING 사용
result = db.execute(
    text("UPDATE request_no_counter SET current_value = current_value + 1 WHERE id = 1 RETURNING current_value")
)
next_value = result.scalar_one()
request_no = f"R-{next_value:010d}"
```
- RETURNING이 안 되는 환경일 경우를 대비한 폴백(UPDATE 후 SELECT)도 구현하되, 우선 RETURNING으로 시도하고 실패 시 폴백하는 방식으로 작성하라. (SQLAlchemy 2.x + 최신 sqlite3라면 RETURNING이 되는 게 일반적이니 먼저 시도해보고 안 되면 폴백 경로로 완성하라)
- 카운터 증가, `requests` INSERT, `request_status_history` INSERT가 **하나의 트랜잭션**에서 처리되어야 한다(이미 1/3에서 구조는 잡혀있음, 카운터 증가만 그 안에 추가).
- 기존 임시 채번 코드(`count()+1`)는 제거한다.

### 2. 접수 수정 API (`PATCH /api/requests/{id}` 또는 `PUT`, 자유롭게 선택하되 완료보고에 명시)

- `app/main/schemas/request.py`에 `RequestUpdate` 스키마 추가 (수정 가능 필드: pickup_date, pickup_location_type, pickup_address, 수량 3개 — business_office_id는 수정 불가로 제외)
- `app/main/services/request_service.py`에 `update_request(db, request_id, data)` 추가:
  - 대상 접수의 `current_status`가 `RECEIVED`(접수)가 아니면 거부 (403 또는 409, 완료보고에 어느 코드를 썼는지 명시)
  - `RequestUpdate`에도 1/3~2/3에서 만든 검증 규칙(수량 합계>=1, 날짜 오늘 이후) 재사용
  - `updated_at` 갱신
- `app/main/api/requests.py`에 라우터 추가

### 3. pytest (`tests/test_request_counter.py`, `tests/test_request_update.py`) — 필수

**test_request_counter.py**:
- `test_counter_increments_sequentially`: 접수 3건 연속 생성 시 request_no가 R-0000000001, 0000002, 0000003으로 정확히 증가
- `test_counter_persists_in_db`: 생성 후 `request_no_counter.current_value`가 실제로 증가했는지 DB 직접 조회로 확인
- `test_counter_rollback_on_failure`: 의도적으로 실패하는 케이스(예: 존재하지 않는 business_office_id로 FK 위반 유도)에서 카운터가 롤백되는지 확인 — 데이터모델 3.3절 6항 "커밋 전 취소 시 카운터도 함께 롤백"을 검증

**test_request_update.py**:
- `test_update_received_status_succeeds`: RECEIVED 상태 접수 수정 성공
- `test_update_non_received_status_rejected`: PICKED_UP 등 다른 상태의 접수는 수정 거부 (아직 상태전이 API가 없으니 테스트 안에서 직접 DB로 status를 바꾼 뒤 검증해도 된다)
- `test_update_persists_changes`: 수정 후 DB 재조회 시 변경된 값 확인
