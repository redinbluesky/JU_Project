# Claude Design 요청 프롬프트 — 복지용구 위탁소독 사용자 인수 테스트 PPT 템플릿

아래 내용을 Claude Design에 그대로 입력해 PowerPoint용 디자인 템플릿과 슬라이드 시안을 생성해 주세요.

---

## 역할

당신은 제품 디자인시스템을 PowerPoint 발표자료로 변환하는 프레젠테이션 디자이너입니다.

목표는 **복지용구 위탁소독 시스템의 사용자 인수 테스트 가이드 PPT**를 만드는 것입니다.
이 PPT는 홍보자료가 아니라 Product Owner가 직접 테스트를 수행하고 결과를 기록하기 위한 실무 문서입니다.

## 참조 디자인시스템

사용자가 제공한 디자인시스템 원본:

```text
D:\Tmp\Wanted Design System
```

가능하다면 원본의 다음 파일과 내용을 시각적 참조로 사용하세요.

```text
styles.css
tokens/colors.css
tokens/typography.css
tokens/layout.css
tokens/fonts.css
tokens/base.css
readme.md
```

원본을 직접 읽을 수 없는 경우에는 아래 토큰을 사용하세요.

### 색상

- Primary: `#0066FF`
- Primary hover/pressed: 더 어두운 blue 계열
- 성공: `#00BF40`
- 오류: `#FF4242`
- 경고: `#FF9E00`
- 페이지 배경: 차가운 밝은 회색
- 본문 텍스트: 진한 cool gray
- 보조 텍스트: 투명도 기반 cool gray
- 테두리: 옅은 inset ring

### 타이포그래피

- Pretendard JP 또는 Pretendard
- 제목: Bold 700
- 섹션 제목: SemiBold 600
- 본문: Medium 500
- 메타·참조: 12~13px 상당
- 한국어 본문 중심
- 영어는 API 경로, QA ID, 상태값 등 기술 식별자에만 사용

### 시각 언어

- 정보 중심
- 차분하고 실무적인 분위기
- 4px spacing rhythm
- 넓은 여백보다 명확한 정보 계층 우선
- border-first inset ring
- 카드 radius는 10~12px
- 과도한 gradient, glassmorphism, 장식용 아이콘 금지
- 상태는 색상과 텍스트를 함께 표시
- 이모지 사용 금지

Wanted 채용 플랫폼의 로고, 회사 로고, 채용 콘텐츠, 브랜드 마크는 사용하지 마세요.
Wanted 디자인시스템의 일반적인 색상·타이포그래피·간격·컴포넌트 분위기만 변환해 사용하세요.

## 출력 형식

- 16:9 PowerPoint 화면 비율
- PowerPoint로 옮기기 쉬운 편집 가능한 슬라이드 구조
- 슬라이드 수: 14~16장
- 각 슬라이드는 제목·핵심 메시지·테스트 절차·판정 기준이 명확해야 함
- 장식보다 테스트 수행 가능성과 가독성을 우선
- 최소 본문 글꼴 크기는 발표 화면에서 읽을 수 있는 크기로 유지
- 표와 단계 흐름은 한 슬라이드에 과도하게 넣지 않음
- 각 슬라이드 하단에 작고 일관된 참조 영역을 둘 수 있도록 설계
- 발표자 노트를 지원한다면 각 슬라이드에 참조 문서와 QA ID를 넣을 수 있는 구조를 제공

## PPT 제목

```text
복지용구 위탁소독 시스템
사용자 인수 테스트 가이드
```

부제:

```text
접수부터 배송완료까지의 업무 흐름 검증
```

## 슬라이드 구성

### 1. 표지

- 제목
- 1단계 기술 프로토타입
- 사용자 인수 테스트 가이드
- 과도한 홍보형 hero 구성 금지

### 2. 테스트 목적과 현재 판정

내용 자리표시자:

```text
자동화 테스트: [실제 테스트 수]
핵심 API·데이터 검증: [통과/조건부]
현재 품질 판정: [출시 가능/조건부 가능/출시 불가]
```

조건부·미검증 항목은 숨기지 않고 명확한 badge로 표시하세요.

### 3. 테스트 준비

- 애플리케이션 실행
- 브라우저 실행
- 테스트 데이터 준비
- 다운로드 폴더 준비
- 개인정보·자격증명 사용 금지

구성: 체크리스트 스타일

### 4. 전체 테스트 흐름

다음 흐름을 수평 또는 단계형으로 표현하세요.

```text
접수 생성
→ 입력 오류 검증
→ 접수 수정
→ 수거완료
→ 소독완료
→ PDF 다운로드
→ 배송완료
→ 목록·필터
→ 통계
→ 엑셀
→ 재시작 후 보존
```

완료 단계는 성공 색상, 현재 테스트 단계는 Primary blue, 미검증 단계는 cool gray로 표현하세요.

### 5. 정상 접수 생성

표 또는 2열 레이아웃:

```text
입력:
- 사업소
- 수거 희망일
- 수거 장소 유형
- 주소
- 품목별 수량

기대 결과:
- 접수번호 생성
- RECEIVED 상태
- 생성 시각 기록
- 최초 상태 이력 생성
```

### 6. 입력 오류 검증

다음 케이스를 표로 표현하세요.

```text
모든 품목 수량 0 → 422, 저장 안 됨
음수 수량 → 422, 저장 안 됨
소수/문자열 수량 → 422
오늘 날짜/과거 날짜 → 422
필수값 누락 → 422
```

각 행에 `입력`, `기대 응답`, `저장 여부` 열을 둡니다.

### 7. 접수 수정

```text
RECEIVED 상태 → 수정 허용
PICKED_UP 이후 → 409
DISINFECTED 이후 → 409
DELIVERED 이후 → 409
```

수정 불가 필드인 `business_office_id`도 표시하세요.

### 8. 상태 전이

주요 흐름:

```text
RECEIVED
→ PICKED_UP
→ DISINFECTED
→ DELIVERED
```

금지 전이:

```text
건너뛰기
역방향
동일 상태 중복
배송완료 이후 변경
```

### 9. PDF 다운로드

상태별 권한 매트릭스:

| 상태 | PDF 결과 |
|---|---|
| RECEIVED | 거부 |
| PICKED_UP | 거부 |
| DISINFECTED | 다운로드 허용 |
| DELIVERED | 다운로드 허용 |

PDF 검증 항목:

- 파일이 열림
- `%PDF` 헤더
- 접수번호 포함
- `기술 프로토타입 - 공단 제출용 아님` 표시

### 10. 목록·필터

- 수거 희망일 기간
- 사업소
- 상태
- 복합 필터

강조 문구:

```text
기간 기준은 생성일이 아니라 수거 희망일입니다.
```

### 11. 통계

- 전체 접수 건수
- 사업소별 접수 건수
- 상태별 접수 건수
- 품목별 수량

정합성 기준:

```text
목록 total = 통계 total = DB 직접 집계
```

### 12. 엑셀 다운로드

필수 10개 열을 표로 보여주세요.

```text
접수번호
사업소
수거 희망일
수거 장소 유형
수거 주소
전동침대 수량
휠체어 수량
기타 소형 용구 수량
상태
완료일
```

수식 인젝션 테스트도 포함하세요.

```text
=SUM(1+1)
+cmd
-cmd
@cmd
```

기대 결과:

```text
수식으로 실행되지 않는 텍스트 셀
```

### 13. 재시작 후 보존

```text
앱 종료
→ 앱 재시작
→ 접수 재조회
→ 상태 재조회
→ 상태 이력 재조회
→ 완료일 재조회
```

기대 결과:

- 접수 데이터 유지
- DELIVERED 상태 유지
- 이력 4건 유지
- sequence 1~4 유지
- completion_date 유지

### 14. 결과 기록 방법

각 테스트 결과를 다음 형식으로 기록하도록 안내하세요.

```text
테스트 ID:
입력:
기대 결과:
실제 결과:
판정: 통과 / 실패 / 조건부 / 미검증
증거: 화면 / 파일 / API 응답 / DB 조회
비고:
```

### 15. 현재 미검증·위험 항목

다음은 숨기지 말고 별도 색상으로 구분하세요.

- PC Chrome 브라우저 검증
- 모바일 375px 검증
- label·aria-live 실제 DOM 검증
- 화면 버튼을 통한 PDF·엑셀 검증
- SQLite 실동시 쓰기 경쟁
- Alembic downgrade 데이터 손실 위험
- runtime 테스트 데이터 초기화 필요

### 16. 최종 판정과 사용자 승인

판정 영역:

```text
출시 가능
조건부 가능
출시 불가
```

현재 기본 자리표시자:

```text
핵심 API·데이터 무결성은 통과했으나
UI·브라우저 검증 결과에 따라 최종 판정이 결정됩니다.
```

사용자 결정 항목:

- UI 미검증 상태를 조건부로 수용할 것인지
- UI 구현 후 브라우저 검증을 완료할 것인지
- 남은 중간·낮은 위험을 수용할 것인지

## 참조 표시 규칙

각 테스트 슬라이드의 하단 또는 발표자 노트에 다음 정보를 기록할 수 있도록 템플릿 공간을 마련하세요.

```text
참조 문서: [문서 경로]
QA ID: [QA-번호]
자동화 테스트: [테스트 파일/테스트명]
증거: [스크린샷/API 응답/파일/DB 조회]
```

최종 슬라이드 또는 부록에는 다음 참조 문서 목록을 넣으세요.

```text
- docs/00-input/원본-요구사항-RFP.md
- docs/10-scope/1단계-기술-프로토타입-목표-범위-인수조건.md
- docs/20-design/시스템-설계.md
- docs/20-design/데이터-모델.md
- docs/20-design/UX-화면-명세.md
- docs/40-quality/인수조건-체크리스트.md
- docs/40-quality/테스트-결과.md
- docs/40-quality/결함-목록.md
```

## 금지사항

- 실제 개인정보나 자격증명 삽입 금지
- 확인되지 않은 테스트 통계나 판정 생성 금지
- 가짜 스크린샷·가짜 성공 수치 생성 금지
- UI가 없는 상태에서 브라우저 테스트가 완료된 것처럼 표시 금지
- 과도한 장식·광택형 gradient·glassmorphism 금지
- Wanted 로고와 채용 플랫폼 콘텐츠 복사 금지

## 산출물

다음 중 가능한 형식으로 생성하세요.

1. PowerPoint 편집 가능한 템플릿 또는 PPTX
2. PPTX 생성이 불가능하면 16:9 슬라이드별 디자인 시안과 정확한 레이아웃 스펙
3. 색상·폰트·간격·표·배지·참조 영역을 재사용 가능한 템플릿으로 분리

이 결과물은 이후 python-pptx로 실제 테스트 데이터와 참조 경로를 채워 최종 PPTX로 생성할 예정입니다.
