# 1단계 기술 흐름 프로토타입 — 목표·범위·인수 조건

## 1. 문서 목적

이 문서는 `JU Project Delivery` 팀이 1단계 기술 흐름 프로토타입을 설계·구현·검수할 때 따를 단일 기준이다.

구현 전 `delivery-lead`가 이 문서와 `../00-input/init.md`, `../00-input/원본-요구사항-RFP.md`를 대조해 실행 계획을 작성한다. 범위 또는 인수 조건을 변경해야 할 경우 구현에 앞서 사용자 승인을 받는다.

## 2. 사업 목표

### 장기 목표

광주·전남 복지용구 위탁소독 업무의 접수, 진행 상태 안내, 소독증명서, 이력 및 통계를 하나의 시스템에서 처리한다.

### 1단계 목표

4~6주 안에 로컬 환경에서 다음 업무 흐름의 기술 가능성을 검증한다.

```text
접수 → 수거완료 → 소독완료 → 배송완료
```

1단계 결과물은 실사용 MVP가 아니라 **기술 흐름 프로토타입**이다. 가상 데이터 1건이 접수부터 배송완료까지 처리되고, 데이터 보존·엑셀·통계가 실제로 작동하면 1단계 목표를 달성한 것으로 본다.

### 다음 단계

1단계 완료 후 협력 사업소 1곳을 대상으로 사용성 검증을 수행한다. 실제 알림톡, 실제 소독증명서, 외부 배포, 인증·권한은 이 검증을 준비하면서 추가한다.

## 3. 실행 우선순위

1. 업무 목표·범위·인수 조건 확정
2. 전체 업무 흐름 완성
3. 사용성
4. 데이터 정확성
5. 자동화

보안·데이터 손실 방지는 위 순위와 무관한 기본 조건이다. 1단계는 로컬 전용이므로 인증을 제외하지만, 외부 배포 전에 인증·권한·개인정보 보호를 필수 적용한다.

### AI 비용 원칙

- 반복적인 설계·개발·검증은 `local-model`을 사용한다.
- 전체 범위, 중요 설계, 일정, 출시 판단은 `delivery-lead`의 `GPT-5.6-sol`을 사용한다.
- Codex Plus 범위에서 시작하고 실제 필요가 확인될 때만 Pro 업그레이드를 검토한다.

## 4. 사용자와 실행 환경

- 1단계 사용자는 개발자 한 명이다.
- 가상 데이터로 개발자 기능 테스트를 수행한다.
- 외부 배포 없이 로컬에서 실행한다.
- 모든 화면은 로그인 없이 사용한다.
- PC Chrome과 모바일 너비의 반응형 화면에서 핵심 흐름을 확인한다.
- 애플리케이션을 종료하고 다시 실행해도 데이터가 유지되어야 한다.

## 5. 기능 범위

### 5.1 접수

접수폼은 다음 정보를 입력받는다.

| 필드 | 규칙 |
|---|---|
| 사업소 | 초기 데이터로 고정 등록된 1~3개 사업소 중 선택 |
| 수거 희망일 | 오늘 이후 날짜만 선택 가능 |
| 수거 장소 유형 | `사업소` 또는 `자택` |
| 수거 주소 | 직접 입력 |
| 전동침대 수량 | 0 이상의 정수 |
| 휠체어 수량 | 0 이상의 정수 |
| 기타 소형 용구 수량 | 0 이상의 정수 |

품목 수량은 최소 한 종류가 1개 이상이어야 한다.

접수 생성 직후:

- 접수번호를 부여한다.
- 최초 상태를 `접수`로 기록한다.
- 생성 시각을 기록한다.
- 화면 알림을 표시한다.

### 5.2 상태 관리

고정 상태는 다음 네 단계다.

```text
접수 → 수거완료 → 소독완료 → 배송완료
```

규칙:

- 접수 1건 단위로 상태를 관리한다.
- 품목은 종류별 수량만 기록한다.
- 품목별 시리얼은 관리하지 않는다.
- 현재 상태의 바로 다음 상태로만 변경할 수 있다.
- 모든 상태 변경 시각을 자동 기록한다.
- 상태 변경 직후 화면 알림을 표시한다.
- 접수 정보는 `접수` 상태에서만 수정할 수 있다.
- 접수 삭제는 허용하지 않는다.
- `배송완료` 전환 시 완료일을 기록한다.

### 5.3 화면 알림

1단계에서는 카카오 알림톡 대신 화면 알림을 사용한다.

화면 알림 발생 시점:

- 접수 생성
- 수거완료 전환
- 소독완료 전환
- 배송완료 전환

화면 알림은 실제 메시지 발송 성공을 의미하지 않는다. 카카오 연동 검증은 다음 단계에서 수행한다.

### 5.4 PDF

- `소독완료` 상태부터 빈 PDF를 다운로드할 수 있다.
- 1단계 PDF는 다운로드 흐름만 검증한다.
- 실제 공단 양식 데이터 삽입과 증명서 유효성은 검증하지 않는다.

### 5.5 접수 목록과 상세

관리자는 접수 목록과 상세 정보를 확인할 수 있다.

필수 필터:

- 수거 희망일 기간
- 사업소
- 상태

기간 필터의 기준 날짜는 수거 희망일이다.

상세 화면에는 다음 정보가 보여야 한다.

- 접수번호
- 사업소
- 수거 희망일
- 수거 장소 유형과 주소
- 품목별 수량
- 현재 상태
- 생성 시각
- 모든 상태 변경 시각
- 완료일

### 5.6 통계 대시보드

통계는 수거 희망일을 기간 기준으로 계산한다.

필수 집계:

- 기간별 접수 건수
- 사업소별 접수 건수
- 상태별 접수 건수
- 전체 품목 총수량
- 전동침대 총수량
- 휠체어 총수량
- 기타 소형 용구 총수량

### 5.7 엑셀 다운로드

엑셀은 현재 필터 결과를 기준으로 내려받을 수 있어야 한다.

필수 열:

- 접수번호
- 사업소
- 수거 희망일
- 수거 장소 유형
- 수거 주소
- 전동침대 수량
- 휠체어 수량
- 기타 소형 용구 수량
- 상태
- 완료일

엑셀 값은 화면 및 저장 데이터와 일치해야 한다.

## 6. 최소 화면

1. 접수폼
2. 접수 목록/상세
3. 통계 대시보드

별도 사업소 관리 화면과 설정 화면은 만들지 않는다. 사업소 1~3개는 초기 데이터로 고정 등록한다.

## 7. 1단계 제외 범위

다음 항목은 구현하지 않는다.

- 카카오 알림톡 실제 발송
- 비즈뿌리오·쏠라피 연동
- 카카오 템플릿 신청 및 승인
- 실제 공단 소독증명서 생성
- PDF에 사업소·품목·시리얼·소독일·직인 삽입
- 외부 또는 클라우드 배포
- 로그인, 인증, 권한 관리
- 기사 계정 및 기사 배정
- 품목별 시리얼 관리
- 사업소 관리 화면
- 접수 삭제
- 상태 건너뛰기 또는 역방향 변경
- 실제 고객 데이터 사용

## 8. 인수 조건

다음 시나리오를 실제로 실행하고 모두 통과해야 완료다.

### 8.1 접수

1. 초기 등록 사업소를 선택한다.
2. 오늘 이후의 수거 희망일을 선택한다.
3. 사업소 또는 자택을 선택하고 주소를 입력한다.
4. 최소 한 품목의 수량을 1 이상 입력한다.
5. 접수를 생성한다.
6. 접수번호, `접수` 상태, 생성 시각이 저장된다.
7. 화면 알림이 표시된다.

### 8.2 입력 검증

- 모든 품목 수량이 0이면 접수가 거부된다.
- 음수 또는 정수가 아닌 수량은 거부된다.
- 오늘 이전 날짜는 거부된다.
- 사업소, 수거 희망일, 장소 유형, 주소가 없으면 접수가 거부된다.

### 8.3 상태 흐름

1. `접수`에서 `수거완료`로 변경한다.
2. `수거완료`에서 `소독완료`로 변경한다.
3. `소독완료`에서 빈 PDF를 다운로드한다.
4. `소독완료`에서 `배송완료`로 변경한다.
5. 각 변경 시각과 화면 알림을 확인한다.
6. 중간 상태를 건너뛰는 변경이 거부되는지 확인한다.
7. 배송완료 시 완료일이 기록되는지 확인한다.

### 8.4 데이터 보존

1. 애플리케이션을 종료한다.
2. 애플리케이션을 다시 실행한다.
3. 접수 정보, 현재 상태, 모든 상태 변경 시각, 완료일이 그대로 유지되는지 확인한다.

### 8.5 조회·통계·엑셀

1. 기간·사업소·상태 필터 결과가 저장 데이터와 일치하는지 확인한다.
2. 접수 건수와 전체·종류별 품목 수량이 일치하는지 확인한다.
3. 엑셀을 다운로드한다.
4. 엑셀의 각 필수 열과 값이 화면 및 저장 데이터와 일치하는지 확인한다.

### 8.6 화면

- PC Chrome에서 접수부터 배송완료까지 수행할 수 있다.
- 모바일 너비에서 가로 스크롤에 의존하지 않고 핵심 흐름을 수행할 수 있다.
- 모든 입력에 식별 가능한 레이블과 검증 오류 메시지가 있다.
- 상태를 색상만으로 구분하지 않는다.

## 9. 완료 보고 형식

각 BOT은 완료를 주장할 때 다음을 보고한다.

```text
완료한 범위:
변경 또는 산출물:
실행한 검증:
실제 결과:
남은 위험:
사용자 결정 필요사항:
```

`quality-gate`는 구현자의 보고를 그대로 승인하지 않고 인수 조건을 독립적으로 실행한다. 모든 조건이 확인되면 `출시 가능`, 일부 비차단 문제가 남으면 `조건부 가능`, 핵심 흐름·데이터·보안 문제가 있으면 `출시 불가`로 판정한다.

## 10. 팀 착수 순서

1. `delivery-lead`: 이 문서를 기준으로 4~6주 실행 계획과 작업 순서를 작성한다.
2. `ux-designer`: 세 화면의 흐름, 필드 상태, 모바일 규칙, 디자인 토큰, 접근성 인수 기준을 작성한다.
3. `local-builder`: 승인된 설계에 따라 최소 구현과 실행 가능한 검증을 작성한다.
4. `quality-gate`: 이 문서의 모든 인수 조건을 독립적으로 검증한다.
5. `delivery-lead`: 결과와 위험을 통합해 사용자에게 보고한다.
