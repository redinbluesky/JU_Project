## 1. 설계 목표

다음 흐름을 단일 로컬 애플리케이션에서 실제로 실행하고 검증한다.

```text
접수 → 수거완료 → 소독완료 → 배송완료
```

설계의 최우선 조건은 다음과 같다.

1. 접수 현재 상태와 상태 변경 이력이 서로 불일치하지 않는다.
2. 허용된 바로 다음 상태로만 전환한다.
3. 애플리케이션을 종료하고 다시 실행해도 데이터가 유지된다.
4. 목록·통계·엑셀이 동일한 DB 원본과 필터 의미를 사용한다.
5. 실제 개인정보, 외부 API 자격증명과 실제 알림톡을 사용하지 않는다.
6. 4~6주 프로토타입을 위해 단일 프로세스와 기존 Java 생태계를 우선한다.

| 사용자 주력 기술 | 일치 | 백엔드는 일치 | 불일치 |

### 3.2 권고 기술 스택

| 영역 | 권고 | 근거 |
|---|---|---|
| Java | OpenJDK 21 LTS | 로컬에 설치되어 있고 장기 지원 버전 |
| 애플리케이션 | Spring Boot 4.0.x 유지보수 라인 | Java 21 호환, 단일 실행 JAR, MVC·검증·테스트 통합 |
| 기준 패치 | 승인·부트스트랩 시점 최신 4.0.x(2026-08-22 관측값 4.0.8) | 구현 시작 시 공식 유지보수 패치와 호환성을 재확인해 고정 |
| 빌드 | Maven Wrapper | 전역 Maven 없이 Windows에서 재현 가능한 실행 |

| 스타일 | 일반 CSS + 승인된 디자인 토큰 | UI 라이브러리 없이 세 화면만 구현 |
| 입력 검증 | Jakarta Bean Validation + 도메인 검증 | 필드 검증과 상태 전이 규칙을 서버에서 강제 |
| 데이터 접근 | Spring Data JPA | 소규모 관계형 모델과 트랜잭션 처리에 충분 |
| DB | H2 2.4.x 파일 모드 | Java 내장형, 단일 로컬 프로세스, 재시작 보존 |
| 스키마 | Flyway | 초기화와 변경 이력을 SQL로 재현 가능하게 보존 |
| PDF | Apache PDFBox 3.0.x | 빈 PDF 생성에 필요한 최소 Java 라이브러리 |
| PDF 기준 패치 | 3.0.7 후보 | 구현 시작 시 보안·호환성 확인 후 고정 |
| 엑셀 | Apache POI 5.5.x | `.xlsx` 생성과 셀 타입 제어 가능 |

Spring Boot, 테스트, JPA, Thymeleaf, H2와 Flyway의 실제 패치 버전은 가능한 한 Spring Boot BOM에서 관리한다. PDFBox와 POI는 직접 버전을 고정하고 의존성 취약점 검토 결과를 남긴다.

### 3.3 선택하지 않는 항목

- React, Vue, Angular 등 별도 SPA 프레임워크
- Next.js 또는 별도 Node 서버
- Docker 필수화
- Redis, 메시지 브로커, 검색엔진
- 마이크로서비스
- 실제 알림톡 SDK
- 인증·권한 프레임워크
- 클라우드 저장소

위 항목은 1단계 범위에 필요하지 않으며 실행·디버깅·인수인계 비용만 늘린다.

## 4. 전체 실행 구조

```text
PC 또는 모바일 Chrome
        │ HTTP / localhost
        ▼
┌──────────────────────────────────────────┐
│ Spring Boot 단일 프로세스               │
│                                          │
│  MVC Controller                          │
│        ↓                                 │
│  Application Service                    │
│        ↓                                 │
│  Domain Rules / Transaction              │
│        ↓                                 │
│  Repository ───────────────┐              │
│        │                    │              │
│        ▼                    ▼              │
│  H2 파일 DB          PDFBox / Apache POI  │
│        │                    │              │
└────────┼────────────────────┼──────────────┘
         ▼                    ▼
 runtime/db/           runtime/pdf/, runtime/xlsx/
```

- 실행 프로세스는 하나다.
- 화면은 서버 렌더링을 기본으로 하고 수량 증감·알림 표시 등 최소 상호작용만 Vanilla JS로 처리한다.
- 업무 규칙은 화면 JavaScript가 아니라 서버 서비스와 도메인 규칙에서 최종 검증한다.
- H2는 파일 모드로 사용하고 메모리 모드를 사용하지 않는다.
- PDF와 엑셀 생성물은 Git 제외 영역인 `runtime/**`에 둔다.

## 5. 권고 애플리케이션 구조

기술 승인 후 `local-builder`가 다음 최소 구조를 구체화한다. 이 경로는 설계안이며 승인 전에는 생성하지 않는다.

```text
app/
├── mvnw
├── mvnw.cmd
├── .mvn/wrapper/**
├── pom.xml
└── src/
    ├── main/
    │   ├── java/.../juproject/
    │   │   ├── JuProjectApplication.java
    │   │   ├── request/       접수·상태·이력
    │   │   ├── dashboard/     목록·상세·통계 조회
    │   │   ├── export/        PDF·엑셀
    │   │   └── common/        공통 오류·시간·웹 설정
    │   └── resources/
    │       ├── templates/     Thymeleaf 화면
    │       ├── static/css/    디자인 토큰과 화면 CSS
    │       ├── static/js/     최소 Vanilla JS
    │       ├── db/migration/  Flyway SQL
    │       └── application.yml
    └── test/
        └── java/.../juproject/
```

패키지는 기술 계층만으로 분리하지 않고 업무 기능별로 묶는다. 1단계에서 재사용되지 않는 인터페이스, 어댑터 또는 플러그인 구조를 미리 만들지 않는다.

## 6. 모듈 책임

| 모듈 | 책임 | 금지 사항 |
|---|---|---|
| `request` | 접수 생성·수정, 상태 전이, 상태 이력, 완료일 | 화면에서 상태를 직접 변경하지 않음 |
| `dashboard` | 목록·상세·필터·통계 조회 | 별도 집계 원본을 만들지 않음 |
| `export` | PDF와 현재 필터 기준 엑셀 생성 | 화면 결과와 다른 쿼리를 임의로 만들지 않음 |
| `common` | 오류 응답, KST 표시, 공통 웹 설정 | 범용 프레임워크성 추상화를 만들지 않음 |

## 7. 핵심 데이터 흐름

### 7.1 접수 생성

```text
접수폼 입력
→ 서버 필드 검증
→ 품목 합계·희망일 도메인 검증
→ 단일 DB 트랜잭션
   ├─ 접수번호 부여
   ├─ 현재 상태=접수 저장
   └─ 최초 상태 이력 저장
→ 커밋
→ 성공 화면 알림
```

접수와 최초 상태 이력 중 하나라도 실패하면 전체 트랜잭션을 롤백한다. 화면 알림은 커밋 성공 후 응답에 포함하며, 알림 표시 실패가 저장된 업무 상태를 되돌리지는 않는다.

### 7.2 접수 수정

```text
수정 요청
→ 접수 조회
→ 현재 상태가 접수인지 확인
→ 서버 입력 검증
→ 수정 저장
→ 커밋
```

현재 상태가 `접수`가 아니면 수정하지 않고 명시적인 오류를 반환한다. 삭제 기능과 삭제 엔드포인트는 만들지 않는다.

### 7.3 상태 전이

```text
상태 변경 요청
→ 접수 조회
→ 현재 상태와 요청 상태 비교
→ 바로 다음 상태인지 확인
→ 단일 DB 트랜잭션
   ├─ 상태 이력 추가
   ├─ 현재 상태 변경
   └─ 배송완료이면 완료 시각·완료일 기록
→ 커밋
→ 성공 화면 알림
```

상태와 이력은 같은 트랜잭션에서 변경한다. 중간 상태 건너뛰기, 역방향, 배송완료 이후 변경과 같은 상태로의 중복 전환은 모두 거부한다.

동시 요청에는 접수 레코드의 낙관적 잠금 버전(`@Version`)을 사용한다. 한 요청이 먼저 커밋되면 뒤 요청은 충돌로 처리하고 상태·이력을 추가하지 않는다.

### 7.4 목록·통계·엑셀

```text
필터 입력
→ FilterCriteria 정규화
→ 공통 조회 조건 생성
   ├─ 목록 조회
   ├─ 통계 집계
   └─ 엑셀 행 조회
```

기간 필터는 항상 수거 희망일을 기준으로 한다. 사업소와 상태 조건의 의미를 목록·통계·엑셀에서 공유하며, 엑셀은 화면에 적용된 현재 필터 값을 그대로 서버에 제출한다.

## 8. 상태 모델과 감사 가능성

고정 상태는 다음 네 값만 사용한다.

```text
RECEIVED(접수)
→ PICKED_UP(수거완료)
→ DISINFECTED(소독완료)
→ DELIVERED(배송완료)
```

각 접수는 현재 상태 한 개와 상태 이력 여러 개를 가진다.

상태 이력에는 최소한 다음 값을 저장한다.

- 상태
- 변경 시각
- 접수 식별자
- 이력 순서 또는 고유 식별자

1단계는 로그인과 계정이 없으므로 변경 사용자를 저장하지 않는다. 다음 단계에서 인증이 추가되면 사용자 식별자를 별도 승인 후 확장한다.

상태 이력은 애플리케이션에서 수정·삭제하지 않는 append-only 데이터로 취급한다. DB 원본 변경은 애플리케이션 정상 흐름에서만 수행한다.

## 9. 시간 처리

- 수거 희망일과 완료일은 `LocalDate`로 저장한다.
- 생성·수정·상태 변경 시각은 `Instant`로 저장하는 것을 권고한다.
- 화면과 엑셀에는 대한민국 표준시(`Asia/Seoul`)로 변환해 표시한다.
- 완료일은 `DELIVERED` 전환 시각을 KST로 변환한 날짜로 기록한다.
- 서버 시각은 서비스 내부의 `Clock`을 통해 가져와 날짜 경계 테스트가 가능하게 한다.

## 10. 영속 저장과 스키마 관리

### 10.1 DB 위치

```text
runtime/db/ju-project
```

- H2 파일 모드를 사용한다.
- 애플리케이션 종료 시 DB 파일을 삭제하지 않는다.
- `create-drop`과 인메모리 DB를 사용하지 않는다.
- 하나의 애플리케이션 프로세스만 DB를 연다.

### 10.2 마이그레이션

- Flyway SQL을 `app/src/main/resources/db/migration/`에 보존한다.
- 스키마 자동 생성은 개발 보조 검증에만 사용하고 정상 실행에서는 Flyway가 기준이다.
- 초기 사업소 1~3개는 고정 식별자를 가진 반복 안전한 마이그레이션으로 등록한다.
- 동일 초기 데이터를 재실행해도 중복되지 않아야 한다.

### 10.3 복구

1단계 최소 복구 방식은 애플리케이션이 종료된 상태에서 `runtime/db/**`를 복사·복원하는 것이다. DB 파일 삭제 또는 초기화 명령은 기본 실행 절차에 포함하지 않는다.

| 접수폼 | GET/POST | `/requests/new`, `/requests` |
| 목록 | GET | `/admin/requests` |
| 상세 | GET | `/admin/requests/{id}` |
| 수정 | POST | `/admin/requests/{id}/edit` |
| 상태 전이 | POST | `/admin/requests/{id}/transition` |
| 통계 | GET | `/admin/dashboard` |
| PDF | GET | `/admin/requests/{id}/disinfection-pdf` |
| 엑셀 | GET | `/admin/requests/export.xlsx` |

1단계는 로그인 없이 로컬에서만 사용한다. 상태 변경과 수정은 GET으로 수행하지 않으며 POST 요청으로 처리한다. 서버는 화면의 비활성화 여부와 관계없이 모든 권한 상태와 입력 규칙을 다시 검증한다.

## 12. 화면 알림

- 접수 생성과 각 상태 전환이 커밋된 후 화면 알림을 표시한다.
- 화면 알림은 외부 메시지 발송 성공을 의미하지 않는다.
- 성공하지 않은 작업에는 성공 알림을 표시하지 않는다.
- 알림에는 상태 변경 내용을 텍스트로 포함한다.
- `role="status"`, `aria-live="polite"`를 적용한다.
- 알림 표시 실패가 업무 트랜잭션을 롤백하지 않는다.

실제 알림톡, Outbox, 재시도와 외부 발송 상태는 1단계에 구현하지 않는다.

## 13. PDF 흐름

- `소독완료` 상태부터 다운로드를 허용한다.
- 서버는 요청 시점에 현재 상태를 다시 확인한다.
- 1단계 PDF는 빈 문서이되 `기술 프로토타입 — 공단 제출용 아님` 표시를 넣는다.
- PDFBox로 최소 한 페이지의 유효한 PDF를 생성한다.
- 생성 파일은 `runtime/pdf/`에 저장하거나 생성 직후 스트리밍하며, 파일을 남길 경우 추측 가능한 원본 DB 식별자를 파일명에 사용하지 않는다.
- 다른 접수의 PDF를 실제 증명서처럼 제공하지 않는다.

외부 URL, 로그인 없는 공유, 만료·취소 링크와 실제 증명서 데이터 삽입은 다음 단계다.

## 14. 엑셀 흐름과 정합성

- 입력은 현재 목록에 적용된 `FilterCriteria`다.
- 목록과 동일한 DB 조회 조건으로 접수 행을 조회한다.
- 열 순서는 승인된 필수 10개 열로 고정한다.
- 날짜와 수량은 문자열로 변환하지 않고 엑셀 날짜·숫자 셀 타입을 사용한다.
- 사용자 입력 문자열이 `=`, `+`, `-`, `@`로 시작하면 수식으로 실행되지 않도록 텍스트 셀로 안전하게 기록한다.
- 생성 결과는 `runtime/xlsx/`에 둔다.

QA는 동일 필터에 대해 다음 값을 대조한다.

1. 화면 행 수
2. DB 원본 행 수
3. 엑셀 행 수
4. 각 필수 열 값
5. 품목별 수량 합계

## 15. 오류 처리와 데이터 손실 방지

| 상황 | 처리 |
|---|---|
| 입력 오류 | 필드별 오류를 표시하고 DB에 저장하지 않음 |
| 잘못된 상태 전이 | 현재 상태와 허용 상태를 포함한 오류를 반환하고 이력 미추가 |
| 동시 상태 변경 | 한 요청만 성공, 나머지는 충돌 처리 |
| PDF 생성 실패 | 업무 상태는 유지하고 다운로드 실패를 표시 |
| 엑셀 생성 실패 | DB를 변경하지 않고 실패를 표시 |
| DB 쓰기 실패 | 트랜잭션 전체 롤백 |
| 애플리케이션 재시작 | 기존 H2 파일에서 데이터 재조회 |

로그에는 실제 개인정보, 전체 주소, 외부 API 키를 기록하지 않는다. 1단계 가상 데이터라도 입력값 전체를 오류 로그에 남기지 않는다.

## 18. 승인 전 확정하지 않는 사항

다음은 이 문서의 권고안이며 사용자 승인 전 확정하지 않는다.

- Spring Boot 4.0.x 채택과 정확한 패치 버전
- Maven Wrapper 채택
- Thymeleaf 서버 렌더링 채택
- H2 파일 DB와 Flyway 채택
- PDFBox와 Apache POI 채택
- 위 모듈·패키지 구조
- `@Version` 기반 낙관적 잠금
- `Instant` 저장과 KST 표시 방식

## 19. 사용자 승인 요청안

### 권고안 A — 승인 권고

```text
Java 21 + Spring Boot 4.0.x + Maven Wrapper
+ Spring MVC/Thymeleaf/Vanilla JS
+ H2 파일 DB/Flyway
+ PDFBox 3.0.x
+ Apache POI 5.5.x
+ JUnit 5/Spring Boot Test
```

장점:

- 현재 설치 환경과 사용자의 Java 역량에 맞음
- 단일 프로세스와 단일 빌드 체계
- 별도 프론트엔드 프로젝트가 없음
- 상태·이력 트랜잭션과 파일 DB 보존을 표준 Java 방식으로 구현 가능
- 4~6주 프로토타입 범위에 가장 작음

단점과 위험:

- H2 파일은 1단계 로컬 검증용이며 실제 다중 사용자 운영 DB로 승인하지 않음
- 첫 빌드 시 Maven Wrapper와 의존성 다운로드에 네트워크 필요
- Spring Boot 4 계열과 라이브러리 호환성을 구현 시작 전에 실제 빌드로 확인해야 함

### 대안 B — Java REST + SPA

사용자 경험 확장에는 유리하지만 별도 프론트엔드 빌드, API 계약, 상태 관리와 테스트 범위가 늘어난다. 1단계에서는 권고하지 않는다.

### 대안 C — SQLite JDBC

H2보다 운영 파일 호환성이 넓지만 JPA 방언·마이그레이션·동시성 검증 부담이 늘어난다. 1단계 단일 Java 프로세스에서는 H2를 우선 권고한다.

## 20. 구현 담당 검토 결과

`local-builder`가 2026-08-22 현재 설계안을 읽기 전용으로 검토했다.

### 판정

- 종합 판정: 승인 가능
- 차단 사항: 없음
- 조건: Spring Boot 4.0.x 기준 최초 프로젝트 생성 후 실제 빌드로 BOM·Flyway·PDFBox·POI 호환성을 확인해야 한다.

### 확인된 사항

- Java 21과 Spring Boot 4.0.x 조합으로 단일 실행 JAR 구성이 가능하다.
- Thymeleaf, H2, Flyway, JUnit 5와 MockMvc는 Spring Boot BOM 관리 범위를 우선 사용할 수 있다.
- PDFBox와 Apache POI는 직접 버전을 고정하고 의존성 트리를 확인해야 한다.
- H2 파일 모드와 Flyway로 재시작 후 데이터 보존을 구현할 수 있다.
- JPA `@Version`으로 동일 접수의 동시 상태 전환 중 하나만 성공하게 검증할 수 있다.
- PDFBox로 빈 PDF 생성 테스트가 가능하다.
- Apache POI로 `.xlsx` 셀 타입·값·수식 주입 방지 테스트가 가능하다.
- Maven Wrapper를 포함하면 전역 Maven 없이 Windows에서 빌드할 수 있다.

### 구현 시작 직후 필수 기술 검증

사용자 기술 승인 후 첫 구현 작업은 기능 개발이 아니라 다음 기술 기반 검증으로 시작한다.

1. Maven Wrapper 실행과 의존성 다운로드
2. Spring Boot 애플리케이션 컴파일·기동
3. BOM이 해석한 H2·Flyway 버전과 호환성 확인
4. PDFBox·POI 직접 버전의 `dependency:tree` 충돌 확인
5. H2 파일 DB 생성·종료·재실행 후 값 보존 확인
6. 최소 PDF·XLSX 생성 테스트

이 검증이 실패하면 기능 구현을 확대하지 않고 승인된 스택의 패치 버전 또는 라이브러리 선택을 재검토한다.
