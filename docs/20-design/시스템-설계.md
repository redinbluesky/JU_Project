## 1. 설계 목표

다음 흐름을 단일 로컬 애플리케이션에서 실제로 실행하고 검증한다.

```text
접수 → 수거완료 → 소독완료 → 배송완료
```

설계의 최우선 조건은 다음과 같다.

1. 접수 현재 상태와 상태 변경 이력이 서로 불일치하지 않는다.
2. 허용된 바로 다음 상태로만 전환한다.
3. 애플리케이션을 종료하고 다시 실행해도 데이터가 유지된다.
4. 목록·통계·엑셀이 동일한 DB 원본과 필터 의미를 사용한다.
5. 실제 개인정보, 외부 API 자격증명과 실제 알림톡을 사용하지 않는다.
6. 4~6주 프로토타입을 위해 단일 프로세스와 Product Owner가 지정한 Python 생태계를 사용한다.

## 4. 전체 실행 구조

```text
PC 또는 모바일 Chrome
        │ HTTP / localhost (uvicorn)
        ▼
┌──────────────────────────────────────────┐
│ FastAPI 단일 프로세스                    │
│                                          │
│  Router (app/main/api/)                  │
│        ↓                                 │
│  Service (app/main/services/) — 도메인 규칙│
│        ↓                                 │
│  SQLAlchemy Session / Transaction         │
│        ↓                                 │
│  Repository ───────────────┐              │
│        │                    │              │
│        ▼                    ▼              │
│  SQLite 파일 DB       reportlab / openpyxl │
│        │                    │              │
└────────┼────────────────────┼──────────────┘
         ▼                    ▼
 runtime/db/           runtime/pdf/, runtime/xlsx/
```

- 실행 프로세스는 하나다 (`uvicorn app.main:app`).
- 화면은 서버 렌더링(Jinja2)을 기본으로 하고 수량 증감·알림 표시 등 최소 상호작용만 Vanilla JS로 처리한다.
- 업무 규칙은 화면 JavaScript가 아니라 서버 서비스와 도메인 규칙에서 최종 검증한다.
- SQLite는 파일 모드로 사용하고 인메모리 모드를 사용하지 않는다.
- PDF와 엑셀 생성물은 Git 제외 영역인 `runtime/**`에 둔다.

```text
app/

├── main/
│   ├── api/                   라우터: requests, dashboard, export
│   ├── models/                 SQLAlchemy ORM 모델
│   ├── schemas/                 Pydantic 요청/응답 스키마
```

## 7. 핵심 데이터 흐름

### 7.1 접수 생성

```text
접수폼 입력
→ Pydantic 스키마 검증
→ 품목 합계·희망일 도메인 검증 (services)
→ 단일 DB 트랜잭션 (SQLAlchemy Session)
   ├─ 접수번호 부여
   ├─ 현재 상태=접수 저장
   └─ 최초 상태 이력 저장
→ commit
→ 성공 화면 알림
```

접수와 최초 상태 이력 중 하나라도 실패하면 전체 트랜잭션을 롤백한다. 화면 알림은 커밋 성공 후 응답에 포함하며, 알림 표시 실패가 저장된 업무 상태를 되돌리지는 않는다.

### 7.2 접수 수정

```text
수정 요청
→ 접수 조회
→ 현재 상태가 접수인지 확인
→ Pydantic 입력 검증
→ 수정 저장
→ commit
```

현재 상태가 `접수`가 아니면 수정하지 않고 명시적인 오류를 반환한다. 삭제 기능과 삭제 엔드포인트는 만들지 않는다.

### 7.3 상태 전이

```text
상태 변경 요청
→ 접수 조회
→ 현재 상태와 요청 상태 비교
→ 바로 다음 상태인지 확인
→ 단일 DB 트랜잭션
   ├─ 상태 이력 추가
   ├─ 현재 상태 변경
   └─ 배송완료이면 완료 시각·완료일 기록
→ commit
→ 성공 화면 알림
```

상태와 이력은 같은 트랜잭션에서 변경한다. 중간 상태 건너뛰기, 역방향, 배송완료 이후 변경과 같은 상태로의 중복 전환은 모두 거부한다.

동시 요청에는 SQLAlchemy 낙관적 잠금(`version_id_col`)을 사용한다. 한 요청이 먼저 커밋되면 뒤 요청은 `StaleDataError`로 처리하고 상태·이력을 추가하지 않는다.

### 7.4 목록·통계·엑셀

```text
필터 입력
→ FilterCriteria 정규화 (Pydantic)
→ 공통 조회 조건 생성
   ├─ 목록 조회
   ├─ 통계 집계
   └─ 엑셀 행 조회
```

기간 필터는 항상 수거 희망일을 기준으로 한다. 사업소와 상태 조건의 의미를 목록·통계·엑셀에서 공유하며, 엑셀은 화면에 적용된 현재 필터 값을 그대로 서버에 제출한다.

## 8. 상태 모델과 감사 가능성

고정 상태는 다음 네 값만 사용한다.

```text
RECEIVED(접수)
→ PICKED_UP(수거완료)
→ DISINFECTED(소독완료)
→ DELIVERED(배송완료)
```

각 접수는 현재 상태 한 개와 상태 이력 여러 개를 가진다.

상태 이력에는 최소한 다음 값을 저장한다.

- 상태
- 변경 시각
- 접수 식별자
- 이력 순서 또는 고유 식별자

1단계는 로그인과 계정이 없으므로 변경 사용자를 저장하지 않는다. 다음 단계에서 인증이 추가되면 사용자 식별자를 별도 승인 후 확장한다.

상태 이력은 애플리케이션에서 수정·삭제하지 않는 append-only 데이터로 취급한다. DB 원본 변경은 애플리케이션 정상 흐름에서만 수행한다.

## 9. 시간 처리

- 수거 희망일과 완료일은 `date`로 저장한다.
- 생성·수정·상태 변경 시각은 timezone-aware `datetime`(UTC)으로 저장하는 것을 권고한다.
- 화면과 엑셀에는 대한민국 표준시(`Asia/Seoul`)로 변환해 표시한다.
- 완료일은 `DELIVERED` 전환 시각을 KST로 변환한 날짜로 기록한다.
- 서버 시각은 테스트 가능하도록 주입 가능한 clock 함수/의존성을 통해 가져온다.

## 10. 영속 저장과 스키마 관리

### 10.1 DB 위치

```text
runtime/db/ju-project.db
```

- SQLite 파일 모드를 사용한다.
- 애플리케이션 종료 시 DB 파일을 삭제하지 않는다.
- 인메모리 DB(`:memory:`)는 정상 실행에 사용하지 않는다 (테스트에서만 허용 가능).
- 하나의 애플리케이션 프로세스만 DB에 쓰기 접근한다.

### 10.2 마이그레이션

- Alembic 버전 스크립트를 `migrations/versions/`에 보존한다.
- 스키마 자동 생성(`Base.metadata.create_all`)은 개발 보조 검증에만 사용하고 정상 실행에서는 Alembic이 기준이다.
- 초기 사업소 1~3개는 고정 식별자를 가진 반복 안전한 마이그레이션(데이터 시딩)으로 등록한다.
- 동일 초기 데이터를 재실행해도 중복되지 않아야 한다 (Alembic 버전 이력으로 재실행 방지).

### 10.3 복구

1단계 최소 복구 방식은 애플리케이션이 종료된 상태에서 `runtime/db/**`를 복사·복원하는 것이다. DB 파일 삭제 또는 초기화 명령은 기본 실행 절차에 포함하지 않는다.

## 11. 화면과 서버 경계

권고 화면/API 경로는 다음과 같다. 최종 경로명은 구현 지시서에서 고정할 수 있다.

| 목록 | GET | `/admin/requests` |

1단계는 로그인 없이 로컬에서만 사용한다. 상태 변경과 수정은 GET으로 수행하지 않으며 POST 요청으로 처리한다. 서버는 화면의 비활성화 여부와 관계없이 모든 권한 상태와 입력 규칙을 다시 검증한다.

## 12. 화면 알림

- 접수 생성과 각 상태 전환이 커밋된 후 화면 알림을 표시한다.
- 화면 알림은 외부 메시지 발송 성공을 의미하지 않는다.
- 성공하지 않은 작업에는 성공 알림을 표시하지 않는다.
- 알림에는 상태 변경 내용을 텍스트로 포함한다.
- `role="status"`, `aria-live="polite"`를 적용한다.
- 알림 표시 실패가 업무 트랜잭션을 롤백하지 않는다.

실제 알림톡, Outbox, 재시도와 외부 발송 상태는 1단계에 구현하지 않는다.

## 13. PDF 흐름

- `소독완료` 상태부터 다운로드를 허용한다.
- 서버는 요청 시점에 현재 상태를 다시 확인한다.
- 1단계 PDF는 빈 문서이되 `기술 프로토타입 — 공단 제출용 아님` 표시를 넣는다.
- reportlab(제안)으로 최소 한 페이지의 유효한 PDF를 생성한다.
- 생성 파일은 `runtime/pdf/`에 저장하거나 생성 직후 스트리밍하며, 파일을 남길 경우 추측 가능한 원본 DB 식별자를 파일명에 사용하지 않는다.
- 다른 접수의 PDF를 실제 증명서처럼 제공하지 않는다.

외부 URL, 로그인 없는 공유, 만료·취소 링크와 실제 증명서 데이터 삽입은 다음 단계다.

## 14. 엑셀 흐름과 정합성

- 입력은 현재 목록에 적용된 `FilterCriteria`다.
- 목록과 동일한 DB 조회 조건으로 접수 행을 조회한다.
- 열 순서는 승인된 필수 10개 열로 고정한다.
- 날짜와 수량은 문자열로 변환하지 않고 엑셀 날짜·숫자 셀 타입을 사용한다.
- 사용자 입력 문자열이 `=`, `+`, `-`, `@`로 시작하면 수식으로 실행되지 않도록 텍스트 셀로 안전하게 기록한다 (openpyxl 제안).
- 생성 결과는 `runtime/xlsx/`에 둔다.

QA는 동일 필터에 대해 다음 값을 대조한다.

1. 화면 행 수
2. DB 원본 행 수
3. 엑셀 행 수
4. 각 필수 열 값
5. 품목별 수량 합계

## 15. 오류 처리와 데이터 손실 방지

| 상황 | 처리 |
|---|---|
| 입력 오류 | 필드별 오류를 표시하고 DB에 저장하지 않음 |
| 잘못된 상태 전이 | 현재 상태와 허용 상태를 포함한 오류를 반환하고 이력 미추가 |
| 동시 상태 변경 | 한 요청만 성공, 나머지는 충돌 처리 (`StaleDataError`) |
| PDF 생성 실패 | 업무 상태는 유지하고 다운로드 실패를 표시 |
| 엑셀 생성 실패 | DB를 변경하지 않고 실패를 표시 |
| DB 쓰기 실패 | 트랜잭션 전체 롤백 |
| 애플리케이션 재시작 | 기존 SQLite 파일에서 데이터 재조회 |

로그에는 실제 개인정보, 전체 주소, 외부 API 키를 기록하지 않는다. 1단계 가상 데이터라도 입력값 전체를 오류 로그에 남기지 않는다.

## 17. 실행 원칙

기술 승인 후 권고 실행 방식은 다음과 같다.

```text
가상환경 생성:      uv venv
의존성 설치:        uv sync (또는 uv pip install -r requirements.txt)
Windows 개발 실행:  uv run uvicorn app.main:app --reload
Windows 테스트:     uv run pytest
Alembic 마이그레이션: uv run alembic upgrade head
```

정확한 명령은 생성된 프로젝트를 실제로 실행한 뒤 README 또는 구현 지시서에 기록한다. 성공을 확인하지 않은 예상 명령을 완료 증거로 사용하지 않는다.
