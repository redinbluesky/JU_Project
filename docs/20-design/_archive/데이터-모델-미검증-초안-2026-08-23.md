## 1. 엔티티 개요

1단계 프로토타입은 이전 버전과 동일하게 세 엔티티로 구성한다.

```
사업소 (BusinessOffice)
  │
  └─ 1:N
       │
       ▼
    접수 (Request)
       │
       └─ 1:N
            │
            ▼
         상태 이력 (RequestStatusHistory)
```

업무 요구사항, 상태 모델, 필터 기준, 제약조건은 언어 독립적이므로 DB-001과 동일하게 유지한다. 변경 대상은 구현 기술(ORM, 마이그레이션 도구, DB 엔진)과 그로 인해 재검토가 필요한 항목(접수번호 생성, 낙관적 잠금, 시간 저장, Enum 저장 방식)이다.

## 2. 테이블 정의

### 2.1 사업소 (business_offices)

초기 등록 1~3개 사업소를 저장한다. 1단계에서는 관리 화면이 없으므로 Alembic 마이그레이션으로 고정 데이터를 등록한다.

| 컬럼 | SQLAlchemy 타입 | SQLite 저장 타입 | 제약 | 설명 |
|------|------|------|------|------|
| id | `Integer` (PK) | INTEGER | PRIMARY KEY (rowid, 자동 증가) | 고유 식별자 |
| code | `String(50)` | VARCHAR(50) | NOT NULL, UNIQUE | 사업소 고유 코드 (고정 값) |
| name | `String(100)` | VARCHAR(100) | NOT NULL | 사업소 이름 |
| created_at | `UTCDateTime`(TypeDecorator, 4절 참조) | DATETIME (UTC 저장, naive) | NOT NULL | 생성 시각 (UTC 저장, 화면·엑셀 출력 시 Asia/Seoul 변환) |

**인덱스**: `code` UNIQUE 인덱스 (제약조건과 동일)

**제약조건**: `code`는 UNIQUE로 중복 방지. 초기 사업소 code UNIQUE는 데이터 무결성 방어 목적.

### 2.2 접수 (requests)

접수 건의 기본 정보와 현재 상태를 저장한다. 품목 수량은 고정 3종 컬럼으로 requests 테이블에 직접 저장한다.

| 컬럼 | SQLAlchemy 타입 | SQLite 저장 타입 | 제약 | 설명 |
|------|------|------|------|------|
| id | `Integer` (PK) | INTEGER | PRIMARY KEY (rowid, 자동 증가) | 고유 식별자 |
| request_no | `String(30)` | VARCHAR(30) | NOT NULL, UNIQUE | 접수번호 (인쇄/엑셀용, `R-{10자리}`) |
| business_office_id | `Integer` (FK) | INTEGER | NOT NULL, FK(business_offices.id) | 사업소 식별자 |
| pickup_date | `Date` | DATE | NOT NULL | 수거 희망일 |
| pickup_location_type | `Enum(PickupLocationType, native_enum=False, length=10)` | VARCHAR(10) + CHECK | NOT NULL | 수거 장소 유형 (`사업소` 또는 `자택`) |
| pickup_address | `String(255)` | VARCHAR(255) | NOT NULL | 수거 주소 |
| current_status | `Enum(RequestStatus, native_enum=False, length=20)` | VARCHAR(20) + CHECK | NOT NULL | 현재 상태 (`RECEIVED`, `PICKED_UP`, `DISINFECTED`, `DELIVERED`) |
| electric_bed_quantity | `Integer` | INTEGER | NOT NULL, CHECK >= 0 | 전동침대 수량 |
| wheelchair_quantity | `Integer` | INTEGER | NOT NULL, CHECK >= 0 | 휠체어 수량 |
| other_small_quantity | `Integer` | INTEGER | NOT NULL, CHECK >= 0 | 기타 소형 용구 수량 |
| completion_date | `Date` | DATE | NULL | 완료일 (DELIVERED 전환 시 기록) |
| created_at | `UTCDateTime` | DATETIME | NOT NULL | 생성 시각 (UTC 저장, 화면·엑셀 출력 시 Asia/Seoul 변환) |
| updated_at | `UTCDateTime` | DATETIME | NOT NULL | 마지막 수정 시각 (UTC 저장, 화면·엑셀 출력 시 Asia/Seoul 변환) |
| version | `Integer` | INTEGER | NOT NULL, DEFAULT 0 | 낙관적 잠금 버전 (SQLAlchemy `version_id_col`) |

**인덱스**:
- `request_no` UNIQUE 인덱스
- `business_office_id` 인덱스
- `current_status` 인덱스
- `pickup_date` 인덱스 (기간 필터용)
- 복합 인덱스 `(business_office_id, current_status)` (목록/통계/엑셀 공통 필터용)

**제약조건**:
- `current_status`는 고정 4값 중 하나만 허용 (SQLAlchemy `Enum(..., native_enum=False)`는 SQLite에서 자동으로 VARCHAR + `CHECK (current_status IN (...))`를 생성한다)
- `pickup_location_type`은 고정 2값 중 하나만 허용 (동일 방식)
- `pickup_date`는 오늘 이전 날짜 저장 금지 (애플리케이션 레벨 검증, DB CHECK로는 강제하지 않음 — "오늘"은 DB 레벨에서 고정할 수 없는 가변 기준이므로 서비스 계층 책임으로 유지)
- `version`은 SQLAlchemy `version_id_col`로 동시 전환 충돌 감지 (8절)
- `electric_bed_quantity + wheelchair_quantity + other_small_quantity >= 1` (테이블 CHECK 제약, `CheckConstraint`로 선언)

**FK**: `business_office_id` → `business_offices.id` (ON DELETE 미지정 — SQLite 기본은 NO ACTION. 1단계는 사업소 삭제 기능이 없으므로 실질적 영향 없음)

### 2.3 상태 이력 (request_status_history)

접수 건의 상태 변경 이력을 append-only로 저장한다. 수정·삭제 불가.

| 컬럼 | SQLAlchemy 타입 | SQLite 저장 타입 | 제약 | 설명 |
|------|------|------|------|------|
| id | `Integer` (PK) | INTEGER | PRIMARY KEY (rowid, 자동 증가) | 고유 식별자 |
| request_id | `Integer` (FK) | INTEGER | NOT NULL, FK(requests.id) | 접수 식별자 |
| status | `Enum(RequestStatus, native_enum=False, length=20)` | VARCHAR(20) + CHECK | NOT NULL | 상태 값 |
| changed_at | `UTCDateTime` | DATETIME | NOT NULL | 변경 시각 (UTC 저장, 화면·엑셀 출력 시 Asia/Seoul 변환) |
| sequence | `Integer` | INTEGER | NOT NULL | 이력 순서 (동일 request_id 기준) |

**인덱스**:
- `request_id` 인덱스
- 복합 인덱스 `(request_id, sequence)` (이력 순서 정렬용)

**제약조건**:
- `status`는 고정 4값 중 하나만 허용
- FK `request_id` → `requests.id` (CASCADE DELETE 없음)
- `id` 단일 PK, `UNIQUE(request_id, sequence)`로 이력 중복 방지

## 3. 접수번호 생성 규칙 (SQLite 재설계)

### 3.1 제약: SQLite는 DB 시퀀스를 지원하지 않는다

기존 설계(DB-001)는 H2 `NEXT VALUE FOR request_no_seq` 방식이었다. SQLite는 `CREATE SEQUENCE` 및 동등 기능이 없다. DEC-003이 승인한 표시 형식(`R-{10자리 일련번호}`, gap 허용, 소비 번호 재사용 안 함)은 그대로 유지하되 채번 메커니즘만 재설계한다.

### 3.2 후보 비교

| 후보 | 방식 | 장점 | 단점 |
|------|------|------|------|
| **A. 카운터 테이블 + 트랜잭션 내 원자적 증가** | `request_no_counter(id=1, current_value)` 단일 행을 트랜잭션 내에서 원자적으로 증가시키고 반환값을 접수번호에 사용 | DEC-003 형식·gap 허용 의미를 그대로 재현, DB 원본 조회로 다음 번호 추적 가능, 사업소 등 다른 카운터로 확장 용이 | 카운터 행에 대한 쓰기 경합 지점이 하나 생김 (1단계는 단일 프로세스·단일 쓰기 연결이므로 영향 작음) |
| B. UUID 기반 | `uuid4()` 등으로 전역 고유 식별자 생성 후 표시용으로 가공 | 채번 경합 없음, 구현 단순 | DEC-003이 승인한 `R-{10자리 숫자}` 형식과 근본적으로 다른 접근이라 재승인 필요, 사람이 읽고 순서를 가늠하기 어려움, 인쇄물 활용성 저하 |
| C. `requests.id`(rowid) 파생 | 행 INSERT 후 발급된 rowid를 `R-{id:010d}`로 변환해 같은 트랜잭션에서 `UPDATE`로 채워 넣음 | 별도 테이블 불필요, SQLite AUTOINCREMENT가 이미 원자적 | id는 PK 용도와 표시 번호 용도가 결합되어 PK 재사용 정책(예: 결번 관리, PK 전략 변경)이 표시 번호에 직접 영향을 줌. INSERT 후 두 번째 UPDATE가 필요해 트랜잭션 내 쓰기가 한 번 더 발생 |

### 3.3 권고안: A. 카운터 테이블 + 트랜잭션 내 원자적 증가

**이유**: DEC-003이 승인한 형식·gap 허용 의미를 다른 후보보다 가장 가깝게 재현하고, PK 전략(id)과 표시 식별자(request_no)의 책임을 분리해 향후 PK 전략이 바뀌어도 접수번호 규칙에 영향이 없다. 1단계 시스템 설계(10.1절)가 이미 "하나의 애플리케이션 프로세스만 DB에 쓰기 접근"을 전제하므로 카운터 행 경합의 실무 위험은 낮다.

**스키마**:

```python
class RequestNoCounter(Base):
    __tablename__ = "request_no_counter"
    id = Column(Integer, primary_key=True)          # 항상 1 (CHECK id = 1)
    current_value = Column(Integer, nullable=False, default=0)
```

- `id = 1` 단일 행만 존재하도록 `CHECK (id = 1)` 제약을 둔다.
- Alembic 초기 마이그레이션에서 `(id=1, current_value=0)` 1행을 시딩한다.

**채번 절차 (접수 생성 트랜잭션 내부)**:

1. 접수 생성 요청이 서비스 계층에 도달하면 하나의 SQLAlchemy 트랜잭션을 연다.
2. 카운터 행을 원자적으로 증가시키고 증가된 값을 즉시 반환받는다.
   - SQLite 3.35 이상(Python 3.11 표준 `sqlite3` 모듈이 링크하는 버전은 통상 이 이상)에서는 `UPDATE ... RETURNING`을 사용한다.
     ```sql
     UPDATE request_no_counter
        SET current_value = current_value + 1
      WHERE id = 1
      RETURNING current_value;
     ```
   - RETURNING을 사용할 수 없는 환경이면 같은 트랜잭션 안에서 `UPDATE` 후 `SELECT current_value FROM request_no_counter WHERE id = 1`로 대체한다. 두 문장 모두 같은 트랜잭션·같은 쓰기 잠금 아래 실행되므로 원자성은 유지된다.
3. 반환된 정수를 10자리 0패딩해 `request_no = f"R-{value:010d}"`로 조립한다.
4. 같은 트랜잭션 안에서 `requests` 행과 최초 `request_status_history` 행을 함께 INSERT한다.
5. 트랜잭션을 commit한다. 카운터 증가, 접수 INSERT, 이력 INSERT 중 하나라도 실패하면 전체가 롤백되어 카운터 값도 되돌아간다(SQLite 트랜잭션 원자성).
6. 트랜잭션이 애플리케이션 예외(검증 실패 등)로 커밋 전에 취소되면 카운터 증가도 함께 롤백되므로, DEC-003이 이미 허용한 "소비 후 롤백으로 인한 gap"은 이 설계에서는 오히려 발생하지 않는다. gap은 (a) commit 이후 다른 이유로 해당 요청이 무효화되는 극히 드문 운영 사례나 (b) 수동 복구 절차에서만 발생할 수 있다.
7. 동시 요청 처리: SQLite는 파일 전체에 대해 쓰기 잠금을 하나만 허용한다. 두 요청이 동시에 카운터를 증가시키려 하면 뒤의 요청은 잠금 대기 후 순차 처리된다(`sqlite3` 연결의 `timeout` 파라미터로 대기 한도를 설정, 초과 시 `OperationalError: database is locked` 반환 — 서비스 계층에서 재시도 또는 오류 응답 처리).

**검증**: `request_no` UNIQUE 제약은 카운터 로직에 결함이 있어도 중복 저장을 최종적으로 막는 방어선으로 유지한다.

### 3.4 표시 형식 (DEC-003 유지)

```
R-0000000001
```

- `R`: 접두사
- `{10자리 일련번호}`: 카운터 테이블에서 생성 (0 패딩)
- gap 허용, 소비된 번호는 재사용하지 않는다. 연속성 보장 안 함.

## 4. 시간 저장 재설계 (Instant → timezone-aware UTC datetime)

### 4.1 문제

Java 버전은 `Instant`(UTC 기준 순간)를 `TIMESTAMP WITH TIME ZONE`으로 저장했다. SQLite는 별도의 timezone-aware 타임스탬프 타입이 없고, 컬럼 선언과 무관하게 값을 문자열/숫자로 저장한다(type affinity). 아무 처리 없이 timezone-aware `datetime`을 그대로 바인딩하면 드라이버가 tzinfo를 버리거나 문자열 표현이 일관되지 않을 수 있다.

### 4.2 설계

- 애플리케이션 내부에서는 항상 timezone-aware `datetime`(UTC, `datetime.now(timezone.utc)`)만 사용한다. naive datetime은 생성하지 않는다.
- DB에는 UTC로 정규화된 뒤 tzinfo를 제거한 naive datetime 문자열(ISO 8601)로 저장한다.
- SQLAlchemy `TypeDecorator`로 왕복 변환을 캡슐화해 저장·조회 시 실수로 naive datetime이 섞이는 것을 막는다.

```python
from datetime import datetime, timezone
from sqlalchemy.types import TypeDecorator, DateTime

class UTCDateTime(TypeDecorator):
    """timezone-aware UTC datetime만 허용. DB에는 UTC naive로 저장하고
    조회 시 tzinfo=UTC를 다시 붙여 반환한다."""
    impl = DateTime
    cache_ok = True

    def process_bind_param(self, value, dialect):
        if value is None:
            return None
        if value.tzinfo is None:
            raise ValueError("UTCDateTime 컬럼에는 timezone-aware datetime만 저장할 수 있다")
        return value.astimezone(timezone.utc).replace(tzinfo=None)

    def process_result_value(self, value, dialect):
        if value is None:
            return None
        return value.replace(tzinfo=timezone.utc)
```

- `created_at`, `updated_at`, `changed_at`은 모두 `UTCDateTime`을 사용한다.
- `pickup_date`, `completion_date`는 시각이 아니라 날짜만 필요하므로 기존과 동일하게 `Date`(timezone 개념 없음)를 유지한다.
- 화면·엑셀 표시 시 `zoneinfo.ZoneInfo("Asia/Seoul")`로 변환한다. 변환은 표시 계층(템플릿/엑셀 생성) 책임이며 DB 저장값은 항상 UTC다.
- 완료일(`completion_date`)은 `DELIVERED` 전환 시각을 KST로 변환한 뒤 그 날짜를 기록한다(시스템 설계 9절과 동일 규칙).
- 서버 시각은 테스트 가능하도록 주입 가능한 clock 함수/의존성을 통해 가져온다(고정값 대체 가능).

## 5. Enum 저장 방식 재설계 (`EnumType.STRING` → SQLAlchemy `Enum`)

- Python `enum.Enum`으로 상태·장소유형을 정의하고 SQLAlchemy `Enum(..., native_enum=False)`로 매핑한다. `native_enum=False`는 SQLite에 네이티브 ENUM 타입이 없으므로 자동으로 `VARCHAR(length) + CHECK (col IN (...))` 조합을 생성한다 — Java `EnumType.STRING`이 문자열로 저장하던 것과 동일한 저장 형태이며 CHECK 제약까지 자동으로 얻는다.

```python
import enum
from sqlalchemy import Enum as SAEnum

class RequestStatus(str, enum.Enum):
    RECEIVED = "RECEIVED"
    PICKED_UP = "PICKED_UP"
    DISINFECTED = "DISINFECTED"
    DELIVERED = "DELIVERED"

class PickupLocationType(str, enum.Enum):
    OFFICE = "사업소"
    HOME = "자택"

# 컬럼 선언 예:
# current_status = Column(
#     SAEnum(RequestStatus, native_enum=False, length=20, validate_strings=True),
#     nullable=False,
# )
```

- `str, enum.Enum`을 함께 상속하면 Pydantic 스키마와 JSON 직렬화에서도 값이 자연스러운 문자열로 다뤄진다(시스템 설계 3.1절 Pydantic v2 검증과 정합).
- `validate_strings=True`로 DB에서 읽은 값이 정의되지 않은 문자열이면 즉시 오류가 나도록 한다(조용한 데이터 오염 방지).

## 6. 낙관적 잠금 재설계 (`@Version` → `version_id_col`)

### 6.1 설계

```python
class Request(Base):
    __tablename__ = "requests"
    # ... 컬럼 생략 ...
    version = Column(Integer, nullable=False, default=0)

    __mapper_args__ = {
        "version_id_col": version,
        "version_id_generator": lambda current_version: (current_version or 0) + 1,
    }
```

- `version_id_col`은 SQLAlchemy ORM이 UPDATE 시 `WHERE version = :expected_version`을 자동으로 추가하고, 영향받은 행이 0건이면 충돌로 판단하게 한다.
- `version_id_generator`를 명시적 증가 함수로 지정해 애플리케이션이 버전 증가 규칙을 통제한다(기본 동작은 자동 증가이지만 명시가 의도를 분명히 한다).
- 신규 INSERT 시 `version` 기본값은 0이다(기존 설계와 동일).

### 6.2 충돌 처리

- 두 요청이 같은 접수 건의 상태를 동시에 전환하려 하면, 먼저 커밋된 요청이 `version`을 증가시킨다.
- 뒤 요청이 flush/commit을 시도하면 SQLAlchemy가 `sqlalchemy.orm.exc.StaleDataError`를 발생시킨다(예상 버전으로 UPDATE했으나 영향받은 행이 0건).
- 서비스 계층은 `StaleDataError`를 잡아 다음을 수행한다:
  1. 현재 세션/트랜잭션을 롤백한다(부분 반영 방지).
  2. 상태 이력에 어떤 행도 추가하지 않는다.
  3. 시스템 설계 15절의 "동시 상태 변경" 처리 규칙에 따라 충돌 응답을 반환한다(재조회 후 재시도를 안내).
- `StaleDataError`는 `requests` 테이블 UPDATE에만 적용된다. `request_status_history`는 append-only INSERT만 발생하므로 버전 컬럼을 두지 않는다(불필요한 확장 방지).

## 9. SQLite 파일 보존과 재시작

### 9.1 DB 위치

```
runtime/db/ju-project.db
```

- SQLite 파일 모드 사용 (`sqlite:///runtime/db/ju-project.db`)
- 애플리케이션 종료 시 DB 파일 삭제 안 함
- 인메모리 DB(`:memory:`)는 정상 실행에 사용하지 않는다(테스트에서만 허용)
- 단일 애플리케이션 프로세스만 DB에 쓰기 접근

### 9.2 재시작 보존

SQLite 파일 모드는 디스크에 영속 저장한다. 애플리케이션 재시작 시 같은 파일을 다시 열어 데이터를 재조회한다. `Base.metadata.create_all()`은 개발 보조 검증에만 사용하고 정상 실행에서는 Alembic이 스키마 기준이다.

### 9.3 복구

1단계 최소 복구 방식은 애플리케이션이 종료된 상태에서 `runtime/db/**`를 복사·복원하는 것이다. DB 파일 삭제 또는 초기화 명령은 기본 실행 절차에 포함하지 않는다.

### 9.4 SQLite 연결 설정 권고

- `PRAGMA foreign_keys = ON` — SQLite는 기본적으로 FK 제약을 강제하지 않으므로 연결마다 명시적으로 켠다(SQLAlchemy 이벤트 리스너 `connect`에서 설정).
- `PRAGMA journal_mode = WAL` — 읽기와 쓰기 동시 접근 시 잠금 경합을 줄인다(단일 쓰기 프로세스 전제와 함께 사용).
- 연결 `timeout`(초 단위, 예: 30)을 설정해 짧은 쓰기 경합에서 즉시 오류를 내지 않고 대기하게 한다.

이 설정들은 DEV-002 실제 구현에서 `app/main/db/`의 엔진 초기화 코드로 확정한다.

## 10. Alembic 초기 데이터와 중복 방지

### 10.1 초기 사업소 등록

고정 1~3개 사업소를 Alembic 마이그레이션의 `upgrade()` 함수 안에서 등록한다. Alembic은 `alembic_version` 테이블로 적용된 리비전을 관리하므로, 앱 재시작 시 같은 리비전이 다시 실행되지 않는다.

```python
# migrations/versions/0001_init_business_offices.py
"""init business_offices"""
from alembic import op
import sqlalchemy as sa
from datetime import datetime, timezone

revision = "0001_init_business_offices"
down_revision = None

def upgrade():
    op.create_table(
        "business_offices",
        sa.Column("id", sa.Integer, primary_key=True),
        sa.Column("code", sa.String(50), nullable=False, unique=True),
        sa.Column("name", sa.String(100), nullable=False),
        sa.Column("created_at", sa.DateTime, nullable=False),
    )
    business_offices = sa.table(
        "business_offices",
        sa.column("code", sa.String),
        sa.column("name", sa.String),
        sa.column("created_at", sa.DateTime),
    )
    now = datetime.now(timezone.utc).replace(tzinfo=None)
    op.bulk_insert(
        business_offices,
        [
            {"code": "OFFICE-001", "name": "가상 사업소 A", "created_at": now},
            {"code": "OFFICE-002", "name": "가상 사업소 B", "created_at": now},
            {"code": "OFFICE-003", "name": "가상 사업소 C", "created_at": now},
        ],
    )

def downgrade():
    op.drop_table("business_offices")
```

`alembic_version`이 리비전 실행 이력을 관리하므로 초기 INSERT 중복 충돌이나 앱 레벨 중복 방지 로직은 필요하지 않다. `business_offices.code` UNIQUE는 예기치 않은 중복 데이터에 대한 DB 무결성 방어로 유지한다.

### 10.2 스키마 초기화

Alembic이 스키마 생성 기준이다. 애플리케이션 기동 시 `Base.metadata.create_all()`을 정상 경로에서 호출하지 않는다(개발 보조 스크립트에서만 예외적으로 사용 가능).

## 11. Alembic 마이그레이션 구조 (Flyway V1~V3 대응)

```
migrations/versions/
├── 0001_init_business_offices.py     # Flyway V1 대응: business_offices 테이블 + 초기 데이터
├── 0002_init_requests_schema.py      # Flyway V2 대응: requests 테이블 + request_no_counter 테이블/시딩
├── 0003_init_request_status_history_schema.py  # Flyway V3 대응: request_status_history 테이블
```

리비전 체인:

```
0001_init_business_offices (down_revision=None)
        ↓
0002_init_requests_schema (down_revision="0001_init_business_offices")
        ↓
0003_init_request_status_history_schema (down_revision="0002_init_requests_schema")
```

- `0001`: business_offices 테이블 생성 + 초기 데이터 3건 시딩 (10.1절)
- `0002`: requests 테이블 생성(FK, CHECK, 인덱스 포함) + `request_no_counter` 테이블 생성 및 `(id=1, current_value=0)` 1행 시딩 (H2 시퀀스를 대체, 3절)
- `0003`: request_status_history 테이블 생성(FK, CHECK, `UNIQUE(request_id, sequence)`, 인덱스 포함)

각 리비전은 `op.create_table`에 `sa.CheckConstraint(...)`와 `sa.Index(...)`를 포함해 CHECK·인덱스가 Alembic만으로 재현되게 한다. 실행 명령은 시스템 설계 17절과 동일하다.

```text
Alembic 마이그레이션 적용: uv run alembic upgrade head
```

## 13. SQLAlchemy 엔진/세션 설정 (권고)

from sqlalchemy import create_engine, event
from sqlalchemy.orm import sessionmaker

engine = create_engine(
    "sqlite:///runtime/db/ju-project.db",
    connect_args={"timeout": 30},
)

@event.listens_for(engine, "connect")
def _set_sqlite_pragma(dbapi_connection, connection_record):

## 17. 자체 정합성 검토

### 17.1 요구사항 일치 확인

| 요구사항 | 매핑 | 비고 |
|----------|------|------|
| 사업소 1~3개 고정 | business_offices 테이블 | Alembic 초기 데이터 |
| 접수 생성 | requests 테이블 | request_no, current_status, timestamps |
| 품목 수량 | requests 컬럼 3개 | >=0 및 합계>=1 제약(CheckConstraint) |
| 현재 상태 | requests.current_status | SAEnum CHECK 제약 |
| append-only 상태 이력 | request_status_history | FK, CASCADE DELETE 없음 |
| 완료일 | requests.completion_date | DELIVERED 시 기록 |
| 생성/수정 시각 | requests.created_at, updated_at | UTCDateTime(UTC 저장, KST 표시) |
| 낙관적 잠금 | requests.version | `version_id_col` + `version_id_generator` |
| 제약조건 | 테이블 CHECK + UNIQUE | 모든 필드 검증 |
| 인덱스 | 목록/통계/엑셀 공통 필터용 | 복합 인덱스 포함 |
| 접수번호 생성 | 카운터 테이블 기반 R-{10자리} | 트랜잭션 내 원자적 증가, gap 허용 |
| 초기 사업소 중복 방지 | UNIQUE + alembic_version | alembic_version으로 재실행 방지 |
| 목록/통계/엑셀 공통 필터 | (business_office_id, current_status) | 복합 인덱스 |
| 재시작 보존 | SQLite 파일 모드 | runtime/db/ju-project.db |
| 복구 | DB 파일 복사·복원 | 애플리케이션 종료 상태 |
| 테스트용 가상 데이터 | pytest fixture/수동 | 실제 고객 데이터 아님 |

### 17.2 데이터 정합성

- requests와 request_status_history: 1:N, FK 연결
- business_offices와 requests: 1:N, FK 연결
- 모든 FK는 CASCADE DELETE 없음 (append-only 원칙)
- SQLite FK 강제는 연결마다 `PRAGMA foreign_keys = ON`이 필요하므로 엔진 `connect` 이벤트에서 매 연결마다 설정한다(13절). 이 설정 누락 시 FK 무결성이 조용히 깨질 수 있으므로 DEV-002 검증 항목에 포함해야 한다.

### 17.3 상태 전이 정합성

- current_status는 고정 4값 중 하나만 허용(SAEnum CHECK)
- request_status_history에 모든 상태 변경 기록
- `version_id_col`로 동시 전환 충돌 감지, 충돌 시 `StaleDataError` → 이력 미추가·롤백
- 완료일은 DELIVERED 전환 시만 기록

### 17.4 필터 정합성

- 기간 필터: pickup_date 기준 (수거 희망일)
- 사업소 필터: business_office_id
- 상태 필터: current_status
- 목록/통계/엑셀 동일한 SQLAlchemy 조회 조건 공유

### 17.5 접수번호 채번 정합성

- 카운터 증가와 requests/request_status_history INSERT가 하나의 트랜잭션에 있으므로 "채번은 됐는데 접수는 실패"하는 상태 불일치가 발생하지 않는다(3.3절 5).
- `request_no` UNIQUE 제약이 최종 방어선으로 남아 있어 카운터 로직 결함이 있어도 중복 저장은 DB 레벨에서 차단된다.

## 18. 문서 검토 결과

- Java/JPA/Flyway/H2 버전(DB-001) 대비 테이블 3개, 컬럼, 제약조건, 인덱스 8개 구조는 변경 없이 유지 확인
- 접수번호 생성: SQLite 시퀀스 미지원 문제를 카운터 테이블 방식으로 재설계, DEC-003 형식·의미 유지 확인
- 낙관적 잠금: `@Version` → `version_id_col`/`version_id_generator`, `StaleDataError` 처리 경로 명시 확인
- 시간 저장: `Instant` → timezone-aware UTC `datetime` + `UTCDateTime` TypeDecorator로 SQLite naive 저장 문제 해결 확인
- Enum: `EnumType.STRING` → SQLAlchemy `Enum(native_enum=False)`로 문자열 저장 + CHECK 자동 생성 확인, Java와 저장 형태 동등성 확인
- 마이그레이션: Flyway V1~V3 → Alembic 리비전 3개 1:1 대응, 초기 사업소 시딩 방법 포함 확인
- 시스템 설계(WP-01R) 9절(시간 처리), 10절(영속 저장), 18절(승인 전 미확정 사항: 접수번호 카운터 구체 구현, 낙관적 잠금 예외 처리)과 정합성 확인 — 이 문서가 해당 미확정 사항의 구체안이다

## 20. 사용자 승인사항 (기존 유지)

1. **접수번호 형식** — `R-{10자리 일련번호}`, gap 허용 — DEC-003 사용자 승인 완료. 이 문서(3절)는 채번 **메커니즘**만 SQLite 제약에 맞춰 재설계했으며 **형식·의미는 변경하지 않았으므로** 별도 재승인 대상이 아니라고 판단한다. 사용자가 이 판단에 동의하지 않으면 21절 "사용자 결정 필요사항"을 검토한다.

## 21. 위험

1. **카운터 테이블 쓰기 경합** — 단일 프로세스 전제가 깨지거나(예: 여러 uvicorn 워커) 트랜잭션이 길어지면 `database is locked` 오류 빈도가 늘 수 있다. DEV-002에서 단일 워커·짧은 트랜잭션 경계를 실측 검증해야 한다.
2. **SQLite RETURNING 절 가용성** — Python 3.11 표준 `sqlite3`가 링크한 SQLite 버전이 3.35 미만이면 `UPDATE ... RETURNING`을 사용할 수 없다. DEV-002 착수 시 `sqlite3.sqlite_version`을 실제 확인하고, 미만이면 2단계(UPDATE 후 SELECT) 방식으로 구현한다.
3. **UTCDateTime TypeDecorator 누락 위험** — 개발자가 실수로 컬럼을 일반 `DateTime`으로 선언하거나 naive datetime을 직접 바인딩하면 KST/UTC 혼선이 재발할 수 있다. 코드 리뷰·테스트에서 모든 시각 컬럼이 `UTCDateTime`을 사용하는지 확인이 필요하다.
4. **SQLite FK 강제 설정 누락** — `PRAGMA foreign_keys = ON`을 연결마다 설정하지 않으면 FK 제약이 조용히 무시된다. DEV-002 검증 항목에 명시적으로 포함해야 한다(17.2절).
5. **`version_id_col` 관련 SQLAlchemy 버전 의존성** — 정확한 예외 처리 방식은 시스템 설계 18절이 이미 "DEV-002 실행 검증 전 확정하지 않음"으로 표시했다. 이 문서 6절은 설계 방향이며, 실제 SQLAlchemy 2.x 동작은 DEV-002에서 실행 테스트로 재확인해야 한다.

## 22. 사용자 결정 필요사항

1. 접수번호 채번 방식으로 3.3절의 **카운터 테이블(후보 A)**을 최종 채택하는 데 동의하는지 확인 필요. 동의하면 DEC-003의 하위 구현 결정으로 기록하고 별도 DEC 번호 없이 진행 가능. 동의하지 않으면 후보 B(UUID) 또는 C(id 파생) 중 재검토 필요.
2. 이 문서(WP-03R) 승인 후 DEV-002(FastAPI 부트스트랩, SQLite 연결, Alembic 마이그레이션 적용, 재시작 보존, 최소 PDF·XLSX 생성) 착수 승인 필요.
