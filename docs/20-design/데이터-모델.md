## 1. 엔티티 개요

1단계 프로토타입은 다음 세 엔티티로 구성한다.

```
사업소 (BusinessOffice)
  │
  └─ 1:N
       │
       ▼
    접수 (Request)
       │
       └─ 1:N
            │
            ▼
         상태 이력 (RequestStatusHistory)
```

## 2. 테이블 정의

### 2.1 사업소 (business_offices)

초기 등록 1~3개 사업소를 저장한다. 1단계에서는 관리 화면이 없으므로 Flyway 마이그레이션으로 고정 데이터를 등록한다.

| 컬럼 | 타입 | 제약 | 설명 |
|------|------|------|------|
| id | BIGINT | PRIMARY KEY, AUTO_INCREMENT | 고유 식별자 |
| code | VARCHAR(50) | NOT NULL, UNIQUE | 사업소 고유 코드 (고정 값) |
| name | VARCHAR(100) | NOT NULL | 사업소 이름 |
| created_at | TIMESTAMP WITH TIME ZONE | NOT NULL | 생성 시각 (Instant 기준, 화면·엑셀 출력 시 Asia/Seoul 변환) |

**인덱스**: `code` UNIQUE 인덱스 (제약조건과 동일)

**제약조건**: `code`는 UNIQUE로 중복 방지. 초기 사업소 code UNIQUE는 데이터 무결성 방어 목적.

### 2.2 접수 (requests)

접수 건의 기본 정보와 현재 상태를 저장한다. 품목 수량은 고정 3종 컬럼으로 requests 테이블에 직접 저장한다.

| 컬럼 | 타입 | 제약 | 설명 |
|------|------|------|------|
| id | BIGINT | PRIMARY KEY, AUTO_INCREMENT | 고유 식별자 |
| request_no | VARCHAR(30) | NOT NULL, UNIQUE | 접수번호 (인쇄/엑셀용) |
| business_office_id | BIGINT | NOT NULL, FK(business_offices) | 사업소 식별자 |
| pickup_date | DATE | NOT NULL | 수거 희망일 |
| pickup_location_type | VARCHAR(10) | NOT NULL | 수거 장소 유형 (`사업소` 또는 `자택`) |
| pickup_address | VARCHAR(255) | NOT NULL | 수거 주소 |
| current_status | VARCHAR(20) | NOT NULL | 현재 상태 (`RECEIVED`, `PICKED_UP`, `DISINFECTED`, `DELIVERED`) |
| electric_bed_quantity | INT | NOT NULL, CHECK >= 0 | 전동침대 수량 |
| wheelchair_quantity | INT | NOT NULL, CHECK >= 0 | 휠체어 수량 |
| other_small_quantity | INT | NOT NULL, CHECK >= 0 | 기타 소형 용구 수량 |
| completion_date | DATE | NULL | 완료일 (DELIVERED 전환 시 기록) |
| created_at | TIMESTAMP WITH TIME ZONE | NOT NULL | 생성 시각 (Instant 기준, 화면·엑셀 출력 시 Asia/Seoul 변환) |
| updated_at | TIMESTAMP WITH TIME ZONE | NOT NULL | 마지막 수정 시각 (Instant 기준, 화면·엑셀 출력 시 Asia/Seoul 변환) |
| version | BIGINT | NOT NULL, DEFAULT 0 | 낙관적 잠금 버전 (@Version) |

**인덱스**:
- `request_no` UNIQUE 인덱스
- `business_office_id` 인덱스
- `current_status` 인덱스
- `pickup_date` 인덱스 (기간 필터용)
- 복합 인덱스 `(business_office_id, current_status)` (목록/통계/엑셀 공통 필터용)

**제약조건**:
- `current_status`는 고정 4값 중 하나만 허용
- `pickup_date`는 오늘 이전 날짜 저장 금지 (애플리케이션 레벨 검증)
- `version`은 JPA `@Version`으로 동시 전환 충돌 감지
- `electric_bed_quantity + wheelchair_quantity + other_small_quantity >= 1` (합계 >= 1)

**FK**: `business_office_id` → `business_offices.id`

### 2.3 상태 이력 (request_status_history)

접수 건의 상태 변경 이력을 append-only로 저장한다. 수정·삭제 불가.

| 컬럼 | 타입 | 제약 | 설명 |
|------|------|------|------|
| id | BIGINT | PRIMARY KEY, AUTO_INCREMENT | 고유 식별자 |
| request_id | BIGINT | NOT NULL, FK(requests) | 접수 식별자 |
| status | VARCHAR(20) | NOT NULL | 상태 값 |
| changed_at | TIMESTAMP WITH TIME ZONE | NOT NULL | 변경 시각 (Instant 기준, 화면·엑셀 출력 시 Asia/Seoul 변환) |
| sequence | INT | NOT NULL | 이력 순서 (同一个 request_id 기준) |

**인덱스**:
- `request_id` 인덱스
- 복합 인덱스 `(request_id, sequence)` (이력 순서 정렬용)

**제약조건**:
- `status`는 고정 4값 중 하나만 허용
- FK `request_id` → `requests.id` (CASCADE DELETE 없음)
- `id` 단일 PK, `UNIQUE(request_id, sequence)`로 이력 중복 방지

## 3. 접수번호 생성 규칙

접수번호는 DB 시퀀스 기반 `R-{10자리 일련번호}` 형식으로 생성한다.

예시: `R-0000000001`

- `R`: 접두사
- `{10자리 일련번호}`: DB 시퀀스에서 생성 (0 패딩)

시퀀스 gap 허용 — 런타임 접수 트랜잭션이 NEXT VALUE를 소비한 후 롤백될 때 gap이 생길 수 있음. 소비된 번호는 재사용하지 않는다. 연속성 보장 안 함.

생성 시점: 트랜잭션 내에서 시퀀스 생성. UNIQUE 제약으로 중복 감지.

## 4. 상태 모델

고정 상태 4값.

```
RECEIVED(접수) → PICKED_UP(수거완료) → DISINFECTED(소독완료) → DELIVERED(배송완료)
```

각 상태 이력에는 최소 다음 값을 저장한다.
- 상태
- 변경 시각
- 접수 식별자
- 이력 순서

1단계는 로그인과 계정이 없으므로 변경 사용자를 저장하지 않는다.

## 5. 목록·통계·엑셀 공통 필터 기준

필터 조건은 다음 세 항목으로 고정한다.

| 필터 | 기준 날짜 | 설명 |
|------|----------|------|
| 기간 | `pickup_date` (수거 희망일) | 기간 필터의 기준 날짜는 수거 희망일 |
| 사업소 | `business_office_id` | 고정 사업소 ID |
| 상태 | `current_status` | 현재 상태 |

목록, 통계, 엑셀은 동일한 DB 조회 조건을 사용한다. 별도 집계 원본을 만들지 않는다.

## 6. H2 파일 보존과 재시작

### 6.1 DB 위치

```
runtime/db/ju-project
```

- H2 파일 모드 사용 (`jdbc:h2:file:runtime/db/ju-project`)
- 애플리케이션 종료 시 DB 파일 삭제 안 함
- `create-drop`과 인메모리 DB 사용 안 함
- 단일 프로세스만 DB 접근

### 6.2 재시작 보존

H2 파일 모드는 디스크에 영속 저장. 애플리케이션 재시작 시 파일에서 데이터 재조회 가능.

### 6.3 복구

1단계 최소 복구 방식은 애플리케이션 종료 상태에서 `runtime/db/**`를 복사·복원. DB 파일 삭제 또는 초기화 명령은 기본 실행 절차에 포함하지 않음.

## 7. Flyway 초기 데이터와 중복 방지

### 7.1 초기 사업소 등록

고정 1~3개 사업소를 Flyway SQL로 등록한다. Flyway는 버전 이력으로 1회 실행된다.

```sql
-- V1__init_business_offices.sql
CREATE TABLE IF NOT EXISTS business_offices (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    code VARCHAR(50) NOT NULL UNIQUE,
    name VARCHAR(100) NOT NULL,
    created_at TIMESTAMP WITH TIME ZONE NOT NULL
);

INSERT INTO business_offices (code, name, created_at) VALUES
    ('OFFICE-001', '가상 사업소 A', CURRENT_TIMESTAMP),
    ('OFFICE-002', '가상 사업소 B', CURRENT_TIMESTAMP),
    ('OFFICE-003', '가상 사업소 C', CURRENT_TIMESTAMP);
```

Flyway는 `flyway_schema_history` 테이블로 적용 이력을 관리하므로, 앱 재시작 시 V1이 다시 실행되지 않는다. 따라서 초기 INSERT 중복 충돌이나 앱 레벨 중복 방지는 필요하지 않다. business_offices.code UNIQUE는 예기치 않은 중복 데이터에 대한 DB 무결성 방어다.

### 7.2 스키마 초기화

Flyway가 스키마 자동 생성 기준. `application.yml`에서 `spring.jpa.hibernate.ddl-auto`는 `none`으로 설정.

---

## 8. @Version 낙관적 잠금

접수 레코드의 동시 전환 충돌 감지를 위해 JPA `@Version` 필드 사용.

```java
@Version
private Long version;
```

한 요청이 먼저 커밋되면 `version` 증가. 뒤 요청은 `OptimisticLockException` 발생. 상태·이력을 추가하지 않고 충돌 처리.

## 11. 테스트용 가상 데이터 원칙

### 11.1 가상 데이터 생성

테스트용 가상 데이터는 테스트 fixture 또는 수동 가상 데이터로 생성. 운영 Flyway 마이그레이션으로 생성하지 않음. 실제 고객 데이터 사용 금지.

### 11.2 가상 데이터 범위

- 사업소: 고정 3개 중 1개 이상 선택
- 접수: 최소 1건, 수거 희망일은 오늘 이후
- 품목: 최소 한 품목 수량 1 이상
- 상태: RECEIVED 시작, 필요시 수거완료/소독완료/배송완료까지 전이

### 11.3 가상 데이터 검증

QA는 동일 필터에 대해 다음 값을 대조.
1. 화면 행 수
2. DB 원본 행 수
3. 엑셀 행 수
4. 각 필수 열 값
5. 품목별 수량 합계

## 12. JPA 엔티티 매핑 방향

### 12.1 Request 엔티티

```java
@Entity
@Table(name = "requests")
class Request {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(name = "request_no", unique = true, nullable = false)
    private String requestNo;

    @ManyToOne
    @JoinColumn(name = "business_office_id")
    private BusinessOffice businessOffice;

    @Column(name = "pickup_date")
    private LocalDate pickupDate;

    @Column(name = "pickup_location_type")
    private String pickupLocationType;

    @Column(name = "pickup_address")
    private String pickupAddress;

    @Enumerated(EnumType.STRING)
    @Column(name = "current_status")
    private RequestStatus currentStatus;

    @Column(name = "electric_bed_quantity")
    private Integer electricBedQuantity;

    @Column(name = "wheelchair_quantity")
    private Integer wheelchairQuantity;

    @Column(name = "other_small_quantity")
    private Integer otherSmallQuantity;

    @Column(name = "completion_date")
    private LocalDate completionDate;

    @Column(name = "created_at")
    private Instant createdAt;

    @Column(name = "updated_at")
    private Instant updatedAt;

    @Version
    private Long version;
}
```

### 12.2 RequestStatusHistory 엔티티

```java
@Entity
@Table(name = "request_status_history")
class RequestStatusHistory {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @ManyToOne
    @JoinColumn(name = "request_id")
    private Request request;

    @Enumerated(EnumType.STRING)
    @Column(name = "status")
    private RequestStatus status;

    @Column(name = "changed_at")
    private Instant changedAt;

    @Column(name = "sequence")
    private Integer sequence;
}
```

### 12.3 BusinessOffice 엔티티

```java
@Entity
@Table(name = "business_offices")
class BusinessOffice {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(name = "code", unique = true, nullable = false)
    private String code;

    @Column(name = "name")
    private String name;

    @Column(name = "created_at")
    private Instant createdAt;
}
```

### 12.4 RequestStatus Enum

```java
public enum RequestStatus {
    RECEIVED,
    PICKED_UP,
    DISINFECTED,
    DELIVERED
}
```

JPA `EnumType.STRING` 사용 — DB에 문자열 저장.

## 13. H2 파일 모드 설정

```yaml
spring:
  datasource:
    url: jdbc:h2:file:runtime/db/ju-project
    driver-class-name: org.h2.Driver
  jpa:
    hibernate:
      ddl-auto: none
    properties:
      h2:
        db:
          settings:
            trace: false
  h2:
    console:
      enabled: false
```

- `ddl-auto: none` — Flyway가 스키마 관리
- H2 콘솔 비활성화 — 1단계 외부 접근 없음

## 15. 자체 정합성 검토

### 15.1 요구사항 일치 확인

| 요구사항 | 매핑 | 비고 |
|----------|------|------|
| 사업소 1~3개 고정 | business_offices 테이블 | Flyway 초기 데이터 |
| 접수 생성 | requests 테이블 | request_no, current_status, timestamps |
| 품목 수량 | requests 컬럼 3개 | >=0 및 합계>=1 제약 |
| 현재 상태 | requests.current_status | CHECK 제약 |
| append-only 상태 이력 | request_status_history | CASCADE DELETE 없음 |
| 완료일 | requests.completion_date | DELIVERED 시 기록 |
| 생성/수정 시각 | requests.created_at, updated_at | Instant 기준 |
| @Version | requests.version | 낙관적 잠금 |
| 제약조건 | 테이블 CHECK + UNIQUE | 모든 필드 검증 |
| 인덱스 | 목록/통계/엑셀 공통 필터용 | 복합 인덱스 포함 |
| 접수번호 생성 | DB 시퀀스 기반 R-{10자리} | gap 허용 |
| 초기 사업소 중복 방지 | UNIQUE + flyway_schema_history | flyway_schema_history로 재실행 방지 |
| 목록/통계/엑셀 공통 필터 | (business_office_id, current_status) | 복합 인덱스 |
| 재시작 보존 | H2 파일 모드 | runtime/db/ju-project |
| 복구 | DB 파일 복사·복원 | 애플리케이션 종료 상태 |
| 테스트용 가상 데이터 | 테스트 fixture/수동 | 실제 고객 데이터 아님 |

### 15.2 데이터 정합성

- requests와 request_status_history: 1:N, FK 연결
- business_offices와 requests: 1:N, FK 연결
- 모든 FK는 CASCADE DELETE 없음 (append-only 원칙)

### 15.3 상태 전이 정합성

- current_status는 고정 4값 중 하나만 허용
- request_status_history에 모든 상태 변경 기록
- @Version으로 동시 전환 충돌 감지
- 완료일은 DELIVERED 전환 시만 기록

### 15.4 필터 정합성

- 기간 필터: pickup_date 기준 (수거 희망일)
- 사업소 필터: business_office_id
- 상태 필터: current_status
- 목록/통계/엑셀 동일한 DB 조회 조건

## 18. 사용자 승인사항

## 19. 위험

1. **시퀀스 gap** — 런타임 트랜잭션이 NEXT VALUE를 소비한 후 롤백되면 gap이 발생할 수 있음. 소비된 번호는 재사용하지 않는다. 연속성 보장 안 함.
2. **Instant 저장** — Instant 저장 시 KST 변환 로직 필요. timezone 설정 확인 필요.
